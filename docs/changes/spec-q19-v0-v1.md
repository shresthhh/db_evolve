## E0001: Run JoinDependentFilterRule before DistributivityRule

Commit `19d14c8bae37`. Files: `src/optimizer/optimizer.cpp`.
Faster when accepted: q19 1.86×.

**Label: general.** This is a pure rule-ordering fix with no constants and no schema or query-specific tests. It lets an existing, principled transformation (deriving per-table filters from a disjunctive join predicate) apply in the common case where every OR branch repeats the join key, which the earlier distributivity rewrite was hiding. Any query of that shape over any schema benefits. TPC-H q19 is the motivating example, but the condition is structural and broad.

- **Mechanism.** The diff moves one existing rule earlier in the rewrite order. JoinDependentFilterRule now runs before DistributivityRule. JoinDependentFilterRule takes a top-level filter of the form OR over AND branches that span several tables. For each table that has single-table conjuncts in every branch, it builds a new filter, OR(branch_1 conjuncts for T, ..., branch_n conjuncts for T), and ANDs these derived filters onto the original predicate. Filter pushdown can then apply them at each table's scan, below the join. In the old order, DistributivityRule ran first. Whenever every OR branch shared a conjunct (typically the join equality), it pulled that conjunct out and turned the root into AND(common, OR(...)). The derived rule only accepts a root OR, so it never fired on that common shape. The change makes the existing transitive-filter derivation reach that case. Distributivity still factors the common term out of the inner OR afterwards.
- **Trigger.** The trigger is unchanged in the rule itself. Only its position in the rule list moved (src/optimizer/optimizer.cpp:53 `rewriter.rules.push_back(make_uniq<JoinDependentFilterRule>(rewriter));` now comes before `DistributivityRule` at :54). Conditions:
(a) The expression is a conjunction with at least one conjunction child (join_dependent_filter.cpp:13-15, `ConjunctionExpressionMatcher` with `Policy::SOME`).
(b) The operator is a FILTER or ANY_JOIN and the expression is the operator's root expression (:56-57 `op.type != LOGICAL_FILTER && op.type != LOGICAL_ANY_JOIN) || !is_root`).
(c) The root is an OR (:63 `!= ExpressionType::CONJUNCTION_OR`).
(d) At least one child is an AND that references more than one table (:71-73 `CONJUNCTION_AND && ExpressionReferencesMultipleTables`).
(e) Some table has non-volatile single-table conjuncts in every branch (:40 `table_idxs.size() != 1` return; :98-100 `Expression does not appear in every conjuncted expression`). Otherwise it returns nullptr (:112).
Behaviour only changes for root ORs whose branches all share at least one identical conjunct. In those cases DistributivityRule (distributivity.cpp:70-83, set intersection, `candidate_set.empty()` abort) would previously have rewritten the root into an AND first. When no common conjunct exists, Distributivity returned nullptr and the rule already fired under the old order. No loop: after the rule returns, ApplyRules recurses with the default is_root=false (expression_rewriter.cpp:29 `return ExpressionRewriter::ApplyRules(op, rules, std::move(result), changes_made);`). In the outer fixpoint loop (:83-86) the root is then an AND, so condition (c) fails.
- **Constants.** None. There are no thresholds, cardinalities, data types or schema names. The only structural conditions are: root OR, an AND branch that spans multiple tables, and a per-table conjunct in every branch. Just outside the trigger: if any branch lacks a predicate on a table, no filter is derived for that table, and if no table qualifies the plan is unchanged (:105-106, :112-113).
- **Outside this benchmark.** This is the classic "derive single-table restrictions from a disjunctive join predicate" (OR-factoring / predicate move-around) optimisation. It now covers the very common shape where the join key is repeated inside each OR branch. That shape is typical of hand-written or ORM-generated SQL written as a comma join with all predicates in WHERE. Examples that are not from TPC-H:
1) SELECT count(*) FROM orders o, customers c WHERE (o.cust_id = c.id AND c.country = 'DE' AND o.amount > 100) OR (o.cust_id = c.id AND c.country = 'FR' AND o.amount > 500);
   Derived: c.country IN ('DE','FR') pushed to the customers scan, and (o.amount > 100 OR o.amount > 500) pushed to the orders scan.
2) SELECT * FROM events e, users u WHERE (e.user_id = u.id AND u.plan = 'pro' AND e.kind = 'click') OR (e.user_id = u.id AND u.plan = 'free' AND e.kind = 'purchase');
In both, the old order factored out `e.user_id = u.id` first and lost the derivation.
- **Otherwise.** If the conditions fail, the rule returns nullptr and the rewriter goes on to DistributivityRule and the remaining rules exactly as before. Rule order relative to all other rules is unchanged. The only change in the result is the extra AND child of derived per-table ORs. These derived filters are implied by the original predicate (which is kept, :119), so results are unaffected. Possible costs: redundant re-evaluation of the derived ORs above the join, and a larger expression tree. The author did not run the existing optimizer tests, and other queries' plans/EXPLAIN output may change.

## E0002: Linear-time union in scan ConjunctionOr filter

Commit `cca0c610d473`. Files: `src/storage/table/column_segment.cpp`.
Faster when accepted: q19 1.61×.

**Label: general.** Both parts are standard techniques. Branchless mask evaluation of a predicate tree with selection compaction is a textbook vectorised-filter approach, and replacing a quadratic union with a bitmap is a straightforward algorithmic fix. The gates are type and shape conditions (numeric type, single column, constant comparisons, no NOT, flat vector) needed for correctness and for the template specialisation. No thresholds are tuned to TPCH sizes, and nothing refers to particular columns, tables or constants. The motivating query is q19 (an OR of BETWEEN ranges on l_quantity), but the code covers the entire broad class of numeric range/equality disjunctions on one column. A minor caveat: a dense mask evaluates every OR branch on every row, with no short-circuit. For highly selective first branches this could in principle do more work than the old path, but it is still bounded by rows × leaves.

- **Mechanism.** The change adds a dense evaluation path for single-column table-scan filters made of AND/OR trees of constant comparisons. Each leaf comparison runs as one branchless loop that writes a 0/1 byte mask over the rows already selected. Masks are combined with &= or |=, and the output selection is emitted in input order, with NULL rows removed through validity at the end. If an earlier filter already reduced the incoming selection, the selected values are first gathered into a compact buffer, so the work stays proportional to the surviving rows. Separately, the generic CONJUNCTION_OR union, which checked every new row against the existing result for duplicates (quadratic), is replaced by a per-row bool bitmap. Each later child only sees rows not yet matched, and the loop stops early once every row has matched.
- **Trigger.** Dense path (TryDenseFilterSelection). It is tried at the top of the CONJUNCTION_OR case (column_segment.cpp:739) and the EXPRESSION_FILTER case (:947). It requires all of the following:
- `approved_tuple_count == 0 || approved_tuple_count > STANDARD_VECTOR_SIZE || vdata.sel->IsSet()` must be false (:659), i.e. a non-empty, flat vector of at most one vector's worth of rows.
- The column's physical type is one of int8..int128, uint8..uint128, float or double (:660-674). This also covers DATE, DECIMAL and TIMESTAMP, which are stored as integers.
- For an ExpressionFilter: the tree contains only BOUND_CONJUNCTION, BOUND_COMPARISON (=, <>, <, >, <=, >=) and BOUND_BETWEEN nodes. Every comparison is between the column, `BoundReferenceExpression>().index == 0 && expr.return_type == type` (:501), and a non-NULL constant of exactly that type, `!value.IsNull() && value.type() == type` (:509).
- For a ConjunctionOr/And TableFilter: every leaf is a CONSTANT_COMPARISON with a non-NULL constant, `!constant_filter.constant.IsNull() && IsDenseComparison(...)` (:432).

Bitmap OR path: taken when the dense path is not applicable, the filter is CONJUNCTION_OR, and no incoming sel index is `>= STANDARD_VECTOR_SIZE` (:748-750).
- **Constants.** The only constant is STANDARD_VECTOR_SIZE (2048 by default). It is DuckDB's compile-time vector size and is used only to size stack buffers and as a safety bound; it is not tuned to this workload. Just outside the bound (scan_count larger than one vector, which happens in some segment scans, or sel indices >= 2048), the code falls back to the original path. Everything else in the trigger is a type or shape test, not a number. NULL constants, NOT, IN, LIKE, functions, casts and multi-column expressions are all rejected.
- **Outside this benchmark.** Any scan with a pushed-down single-column filter that is an AND/OR (or BETWEEN) combination of constant comparisons on a numeric, decimal, date or timestamp column. Two examples:
- `SELECT count(*) FROM orders_log WHERE amount BETWEEN 10 AND 20 OR amount BETWEEN 100 AND 200 OR amount > 5000;` with amount a DECIMAL or DOUBLE column. This is pushed as an EXPRESSION_FILTER.
- `SELECT * FROM events WHERE ts_day = DATE '2024-01-01' OR ts_day = DATE '2024-03-01' OR ts_day >= DATE '2024-12-01';` This is a ConjunctionOrFilter of constant comparisons.

Any query with an OR filter that falls back to the generic per-child loop (for example over string columns or mixed filter kinds) also gets the linear bitmap union.
- **Otherwise.** When the dense trigger fails, the CONJUNCTION_OR case uses the new bitmap union if all indices are < STANDARD_VECTOR_SIZE (:748-750). Otherwise it runs the original quadratic loop unchanged. The EXPRESSION_FILTER case falls through to the original ExpressionExecutor::SelectExpression code (:952 onward), which is unchanged. Other filter types are not affected.
