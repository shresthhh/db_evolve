## E0003: Parallel combine and parallel source for large perfect hash aggregate (re-land E0001)

Commit `3f681052d028`. Files: `src/execution/operator/aggregate/physical_perfecthash_aggregate.cpp`, `src/execution/perfect_aggregate_hashtable.cpp`, `src/execution/physical_plan/plan_aggregate.cpp`, `src/include/duckdb/execution/operator/aggregate/physical_perfecthash_aggregate.hpp`, `src/include/duckdb/execution/perfect_aggregate_hashtable.hpp`.
Faster when accepted: q13 1.25×.

**Label: heuristic.** The techniques are standard and general: a direct-mapped (perfect hash) aggregate for dense integer keys, lock-striped parallel merge of thread-local tables, and morsel-parallel output scan. They are gated by natural conditions (integer keys, min/max stats, density, memory), and none of them refers to TPCH tables or columns. Any dense-integer-key GROUP BY in the 4K-4M group range benefits. It is not fully "general" because the new planner ceiling of 22 bits is a magic number. It sits just above what TPCH q13 at SF10 needs (c_custkey, 21 bits), and the 1/4 density and 1/8 memory fractions are hand-chosen rather than derived. Upstream would plausibly accept it, possibly with a configurable or memory-derived cap instead of a fixed 22.

- **Mechanism.** Before this change, DuckDB's perfect-hash GROUP BY was only used when the integer group keys' min/max range fit in perfect_ht_threshold bits (12 by default, about 4K slots). Now it can also be used up to 22 bits (about 4M slots), but only when the estimated group count is at least a quarter of the slot count and every thread's private table fits in 1/8 of the memory limit. For large tables (2^16 slots or more), the operator now merges thread-local tables in parallel: the slot array is split into up to 64 vector-aligned stripes, each with its own mutex, and threads take them in rotation. Before, one global lock made the merge serial. The output scan is also parallel now: threads claim 16384-slot blocks from an atomic counter, each with its own address vector and arena. Before, the scan ran on a single thread.
- **Trigger.** Planner (plan_aggregate.cpp), all of these must hold:
- Single grouping set and no GROUPING() functions: `if (op.grouping_sets.size() > 1 || !op.grouping_functions.empty()) return false;` (:133).
- No partitioned aggregate was chosen first (:313).
- Every group key has an integer physical type with min/max stats (:142-180).
- The summed bits are within the new cap: `if (perfect_hash_bits > MaxValue<idx_t>(threshold, LARGE_PERFECT_HT_MAX_BITS))` (:236), with `LARGE_PERFECT_HT_MAX_BITS = 22` (:130).
- No DISTINCT aggregates, and every aggregate has a combine callback (:244).
- When bits > threshold (default "12", settings.hpp:1340), two extra guards apply: `if (!op.has_estimated_cardinality || op.estimated_cardinality < total_groups / 4) return false;` (:253) and `if (threads * total_groups * (state_size + 1) > max_memory / 8) return false;` (:258).

Executor (physical_perfecthash_aggregate.cpp):
- The parallel combine and parallel scan run only when `parallel = total_groups >= PERFECT_HT_PARALLEL_MIN_GROUPS` (:95), with `PERFECT_HT_PARALLEL_MIN_GROUPS = idx_t(1) << 16` (:84).
- Otherwise the code takes `if (!gstate.parallel) { lock_guard ...; gstate.ht->Combine(*lstate.ht);` (:195), and the source block is the whole table, so MaxThreads is 1 (:225, :229).

Note that the parallel executor path also applies to tables of 13-16+ bits that a user reaches by raising perfect_ht_threshold.
- **Constants.** - **22 bits (4M slots), :130.** This cap is not derived from hardware; it is a hand-picked ceiling. TPCH q13 at SF10 groups on c_custkey, which has 1.5M dense values and needs 21 bits, the "2M slots" in the issue. 22 leaves one bit of headroom (about SF20). Above it (for example 8M distinct keys) the planner falls back to the radix hash aggregate, the old behaviour. Plausibly chosen with this workload's size in mind, but it is a reasonable order of magnitude for a dense direct-mapped table.
- **Density 1/4, :253.** A principled sparsity guard: it bounds wasted slots to about 4x the groups. Because bits are rounded up from range+2, a key whose estimated distinct count covers its whole range is always at least 1/2 dense, so dense surrogate keys pass easily. Just below 1/4 (a sparse key, or a low estimate after selective filters), the hash aggregate is used. It depends on the cardinality estimate, which can be wrong in either direction.
- **Memory max_memory/8 across threads*slots*(state_size+1), :258.** A principled guard that accounts for one full table per thread (the +1 is the group_is_set byte). It ignores the group-key storage in tuple_size, so it slightly underestimates. Exceeding it falls back to the hash aggregate.
- **2^16 parallel threshold, :84.** A generic cutoff below which parallelism isn't worth it; under it the exact old serial code runs.
- **64 stripes, :86.** Generic lock-striping granularity.
- **Scan block of STANDARD_VECTOR_SIZE*8 = 16384 slots, :88.** Generic morsel size.

None of these encode TPCH schema or column names.
- **Outside this benchmark.** Any GROUP BY on one or more integer columns whose min/max statistics give a combined range of 2^13 to 2^22 slots, that is reasonably dense (estimated groups at least a quarter of the slots), has no DISTINCT or GROUPING SETS, and fits the memory guard. Typical cases are aggregates keyed by dense surrogate or foreign keys (user_id, product_id, order_id up to about 4M), and grouping on small-range integers such as date parts combined with an id.

Examples, not from TPCH:
1. `SELECT user_id, count(*), sum(amount) FROM events GROUP BY user_id;` where events.user_id is roughly 1..1,000,000 (20 bits, dense).
2. `SELECT film_id, store_id, count(*) FROM rentals GROUP BY film_id, store_id;` with film_id in 1..200000 (18 bits) and store_id in 1..8 (4 bits), 22 bits total, if most combinations occur.

Before this change, both went to the radix hash aggregate under the default 12-bit threshold. Queries with sparse keys (for example hashed ids, or ids that skip widely) do not qualify.
- **Otherwise.** Planner: if any new guard fails (more than 22 bits, no estimate, density below 1/4, or the memory bound is exceeded), CanUsePerfectHashAggregate returns false and the regular PhysicalHashAggregate is planned (:329), the old behaviour. At or below perfect_ht_threshold the planner decision is unchanged. Executor: for tables under 2^16 slots, Combine takes the original single-lock full Combine (:195-198). The source uses one block covering the whole table, so MaxThreads is 1 and the scan is serial as before. The old Scan(pos, result) and Combine(other) now delegate to CombineRange/Scan over the full range with the table's own arena, which keeps the behaviour equivalent.

## E0004: Perfect hash join for RIGHT joins on dense unique build keys

Commit `6d8309dd1704`. Files: `src/execution/operator/join/perfect_hash_join_executor.cpp`, `src/execution/operator/join/physical_hash_join.cpp`, `src/include/duckdb/execution/operator/join/perfect_hash_join_executor.hpp`, `src/optimizer/join_filter_pushdown_optimizer.cpp`.
Faster when accepted: q13 1.24×.
Numeric constants in added code: `4194304`.

**Label: heuristic.** Extending perfect (direct-indexed) hash joins to right/build-preserving outer joins, tracking matches per slot, is a standard, principled technique. The off-by-one fix is a real bug fix that helps any join on a dense unique key. Both apply to a broad, natural class of joins on surrogate keys, nothing like a query-specific branch. However, the new 2^22 range ceiling has no stated derivation, and it is exactly what lets a 1.5M-row customer key range (q13 at SF10) take the path, so it looks chosen for this workload's sizes. The 25% density and max_memory/8 guards are reasonable but arbitrary. Upstream would plausibly accept this, possibly with different constants, so it is "heuristic" rather than "general".

- **Mechanism.** DuckDB's perfect hash join replaces hashing with direct array indexing: slot = key - build_min. Before this change it ran only for INNER joins whose build key range was at most 2^20. It now also runs for RIGHT outer joins, where the build side is preserved. For these joins it keeps two per-slot arrays: the address of the build tuple (slot_to_row) and a matched byte (slot_found). Probes set the matched byte. After probing ends, PropagateFoundMatches writes the bytes into the normal hash table's per-tuple match flag, so the existing scan for unmatched build rows works unchanged. The change also does three other things: (a) build key ranges up to 2^22 are allowed when the keys are dense enough and the table fits in memory; (b) an off-by-one in the duplicate early-out is fixed (Count > range becomes Count > range+1), which previously rejected every fully dense unique key set, INNER joins included; (c) the optimizer now computes the build-side min/max for RIGHT joins even when no table scan takes the pushed-down filter, so the perfect path can get key bounds.
- **Trigger.** The hash join must be in memory (not external): physical_hash_join.cpp:949 "if (sink.external) { ... sink.perfect_join_executor.reset();". In CanDoPerfectHashJoin all of the following must hold:
- Join type and condition: "(op.join_type != JoinType::INNER && op.join_type != JoinType::RIGHT) || op.conditions.size() != 1 || ... != COMPARE_EQUAL || !TypeIsInteger(key_type.InternalType())" → return false (perfect_hash_join_executor.cpp:73).
- No STRUCT, LIST or ARRAY columns on the build side (:79-88).
- Key bounds present: "if (min.IsNull() || max.IsNull()) return false" (:91).
- Range ceiling: "build_range > MAX_DENSE_BUILD_SIZE (4194304)" → false (:113-115).
- For ranges between 2^20 and 2^22, two more checks: density "ht.Count() * 4 < build_size" → false (:119), and memory "build_size * slot_size > ht.buffer_manager.GetMaxMemory() / 8" → false (:127), where slot_size = 8 + 1 + the sum of the build output type sizes.
- Duplicate early-out: "ht.Count() > build_range + 1" → false (:135).
- The build fill must then confirm the keys are unique.
The bounds for RIGHT joins come from the change in join_filter_pushdown_optimizer.cpp:275: "compute_aggregates_anyway = (join.join_type == JoinType::INNER || join.join_type == JoinType::RIGHT) && join.conditions.size() == 1 && ... COMPARE_EQUAL && TypeIsIntegral(...)".
- **Constants.** - MAX_BUILD_SIZE = 2^20 (1,048,576): the existing upstream constant, unchanged.
- MAX_DENSE_BUILD_SIZE = 2^22 (4,194,304): new. It is a round power of two (4× the old cap) with no stated derivation. It is the constant that lets a 1.5M-key build side through: TPC-H customer at SF10 has 1.5M rows, so the old 2^20 cap blocked q13's customer build. So 2^22 is at least compatible with, and plausibly picked for, the benchmark's sizes. It would still admit customer up to about SF27. Just outside it (range > 4,194,304) the join falls back to the regular hash join, as any range > 2^20 did before.
- Density factor 4 (at least 25% of slots occupied): a principled guard against sparse arrays, though the value is arbitrary. TPC-H surrogate keys are 100% dense, so they pass with a wide margin. A build with keys spaced 5 apart over a range above 2^20 falls back.
- Memory budget of max_memory/8: a conservative fraction of the configured memory limit, not tuned to the workload. With little memory configured, large-range builds fall back.
- The change from `Count > range` to `Count > range+1` is a correctness fix of an off-by-one (a range of max-min has max-min+1 slots), not a tuned value.
- **Outside this benchmark.** Any in-memory RIGHT join that the planner produces, including a LEFT JOIN whose sides the optimizer swapped so the preserved side is the build. It needs a single integer equality key with unique, dense values on the build side, such as a surrogate or serial primary key, and a key range of at most 2^20, or at most 2^22 if at least 25% of slots are occupied. The off-by-one fix also enables the existing perfect path for INNER joins on fully dense unique keys. Typical case: counting children per parent while keeping parents with zero children.
Example 1: SELECT u.id, count(e.event_id) FROM users u LEFT JOIN events e ON e.user_id = u.id AND e.kind = 'click' GROUP BY u.id; where users.id is a serial 1..2,000,000 and events is large, so the planner builds on users.
Example 2: SELECT p.product_id, p.name, s.qty FROM sales s RIGHT JOIN products p ON s.product_id = p.product_id; with products.product_id = 1..500,000 (unique).
Example 3 (INNER, enabled by the off-by-one fix): SELECT * FROM fact f JOIN dim d ON f.dim_id = d.id; where dim.id is exactly 1..N.
- **Otherwise.** If any condition fails (other join types such as LEFT, FULL, SEMI or ANTI where the build is not preserved in the RIGHT sense, more than one condition, non-integer keys, NULL or absent min/max, a range above 2^22, a large range that is too sparse or too big for memory, duplicate keys found by the early-out or the build fill, or an external join), perfect_join_executor is reset and the regular hash join runs unchanged (physical_hash_join.cpp:1016-1019). For INNER joins nothing changes except the off-by-one fix and the new skipping of NULL keys in the build fill. The extra min/max aggregate computation for RIGHT joins happens even when the perfect path is then rejected; it is a small extra cost.
