## E0001: Run JoinDependentFilterRule before DistributivityRule

Commit `b34cc9b9af5b`. Files: `src/optimizer/optimizer.cpp`.
Faster when accepted: q19 1.92×.

**Label: general.** This is a principled phase-ordering fix with no constants. Under the old order, DistributivityRule turned the root into an AND before JoinDependentFilterRule ran, so the rule was effectively dead for any OR whose branches shared a conjunct. That covers any shared conjunct in any schema, not just Q19's. The trigger is purely structural and broad. The benefit (filters pushed down to scans) applies to any query of this shape. The worst case is a slightly redundant extra predicate.

Caveats:
- Only Q19 improved in this benchmark.
- The author did not run the optimizer or plan-snapshot tests, and plan outputs for other queries' OR filters may have changed.
- The rule still only fires on root ORs. A cross-table OR nested under an AND, for example one written next to other WHERE conjuncts, is not covered.

- **Mechanism.** Two expression-rewriter rules now run in a different order; neither rule's code changed. JoinDependentFilterRule takes a top-level OR of AND-branches that span several tables. For each table that has a predicate in every branch, it adds the OR of those per-table predicates as an extra single-table conjunct, and the extra conjunct can then be pushed below the join into the scan. Before the change, DistributivityRule ran first. If the OR branches shared any conjunct (in TPC-H Q19, the join key p_partkey = l_partkey), it factored that conjunct out and turned the filter's root into an AND. JoinDependentFilterRule only acts on a root OR, so it never fired on such filters. With the new order it fires first, and DistributivityRule still factors the inner OR afterwards. This fixes an ordering bug that hid an existing, standard derivation (pushing a disjunction's implied per-table predicates down to the scans).
- **Trigger.** Rules run in list order on each node (src/optimizer/expression_rewriter.cpp:14 `for (auto &rule : rules)`), and the first rule that rewrites a node wins. The recursive pass on the rewritten node uses the default `is_root = false` (expression_rewriter.hpp:41). The new path needs all of the following:
- The operator is a FILTER or ANY_JOIN and the expression is the root: join_dependent_filter.cpp:56-57 `op.type != LOGICAL_FILTER && op.type != LOGICAL_ANY_JOIN) || !is_root`.
- The root is an OR: :63 `!= ExpressionType::CONJUNCTION_OR`.
- At least one child is an AND that references more than one table: :71-73 `CONJUNCTION_AND && ExpressionReferencesMultipleTables(*child)`.
- At least one table has a non-volatile conjunct that references only that table, and it appears in every branch: :37 `!expression.IsVolatile()`, :40 `table_idxs.size() != 1`, :98-100 `found = false`.

The change only matters when the OR branches also share some identical conjunct (DistributivityRule's candidate_set is non-empty, distributivity.cpp:81 `if (candidate_set.empty()) return nullptr`). That conjunct can be a join key or a shared single-table predicate. Without one, the old order also reached JoinDependentFilterRule.
- **Constants.** None. The diff only moves one rule registration (optimizer.cpp:52 added, old line 69 removed). It adds no thresholds, sizes or statistics. The rule's own conditions are structural: root OR, AND children, exactly one table per extracted conjunct.
- **Outside this benchmark.** Any filter or non-equi join whose condition is an OR of AND-branches across two or more tables, where the branches repeat a common conjunct and every branch also has predicates on the same table. This shape is common in hand-written and ORM-generated SQL that repeats the join key or a status predicate inside each branch.

Example 1:
SELECT * FROM orders o, customers c WHERE (o.cust_id = c.id AND c.country = 'DE' AND o.amount > 100) OR (o.cust_id = c.id AND c.country = 'FR' AND o.amount > 500);
Now derives c.country IN ('DE','FR') and (o.amount > 100 OR o.amount > 500) at the scans.

Example 2 (shared conjunct is not a join key):
SELECT * FROM tickets t JOIN agents a ON t.agent_id = a.id WHERE (t.status = 'open' AND a.team = 'billing' AND t.prio > 3) OR (t.status = 'open' AND a.team = 'tech' AND t.prio > 1);
Before, t.status = 'open' was factored out first, so no a.team filter was derived. Now a.team IN-style disjunction is pushed to agents.
- **Otherwise.** If the expression is not a root OR in a FILTER or ANY_JOIN, or no table is constrained in every branch, JoinDependentFilterRule returns nullptr (join_dependent_filter.cpp:58/64/79/113). The remaining rules then run in their old relative order, so DistributivityRule factors as before. When the rule does fire, the original OR is kept (:119 `result_conjunction.children.push_back(conjunction.Copy())`) and the derived filters are added alongside it, so results stay the same. The cost is redundant predicate evaluation. On the next fixpoint iteration the root is an AND, so the rule rejects it at :63 and does not loop.

## E0002: Length-aware selectivity for contains()/LIKE scan filters v2

Commit `f824d63b0fe7`. Files: `src/optimizer/join_order/relation_statistics_helper.cpp`.
Faster when accepted: q09 1.64×, q13 1.05×.
Numeric constants in added code: `0.01`, `0.75`.

**Label: heuristic.** The idea is general and well known: pattern selectivity that shrinks with literal length, as in PostgreSQL. It applies to a broad, natural class of queries and does not test for any benchmark schema, column, or literal. However, the decay of 0.75 per character and the 1% floor are arbitrary, uncalibrated constants that ignore column statistics. The author validated them only by the q09 speedup, and the author also noted the side effect that lineitem lost its bloom filter. Upstream might accept the idea with different constants or a data-driven estimate, so it is general in kind but heuristic in its numbers.

- **Mechanism.** The join-order optimizer estimates the cardinality of each base-table scan. Before this change, any string-match filter pushed into the scan got the flat default selectivity of 0.2. Now, for positive substring or pattern matches against a constant string (contains, LIKE, prefix, suffix), the estimate depends on the length of the literal: selectivity = max(0.2 * 0.75^L, 0.01), where L is the number of literal characters in the pattern, not counting % and _ for LIKE. A longer pattern therefore gives a smaller estimated scan, which can change the join order. In q09, the `p_name LIKE '%green%'` filter (rewritten to contains, L=5) drops from 0.2 to about 0.047, so the part relation looks roughly 4x smaller. This is a crude, data-independent heuristic in the same family as the classic System R / PostgreSQL fixed-per-character pattern selectivity. It does not use any column statistics.
- **Trigger.** All of the following must hold:
- The table filter pushed into a LogicalGet that has column statistics is `case TableFilterType::EXPRESSION_FILTER` (relation_statistics_helper.cpp:474). These filters are only created by `TryPushdownGenericExpression` when the scan has `get.function.pushdown_expression` and the expression references exactly one column (filter_combiner.cpp:379-394, 405).
- The expression is a BOUND_FUNCTION named `"~~" || "like_escape"` or `"contains" || "prefix" || "suffix"` (relation_statistics_helper.cpp:495-499). NOT LIKE, ILIKE, regexp and similar functions are excluded.
- `children[0]` is not foldable and `children[1]` is a BOUND_CONSTANT (:500-503).
- The constant is non-NULL and of type VARCHAR (:505).
- InspectTableFilter is only reached when `column_statistics` is non-null (:135-137).

Results are combined with other filters on the same table by `MinValue` (:138). The new value wins only when it is smaller than the estimates from the other filters. Any non-default value also makes `has_equality_filter` true (:147), so the flat 0.2 override no longer applies.
- **Constants.** - 0.2 (DEFAULT_SELECTIVITY, relation_statistics_helper.hpp:57): the engine's existing default. With L=0 the estimate matches the old behaviour, so there is no discontinuity at the low end.
- 0.75 per character: an ad-hoc decay factor in the spirit of PostgreSQL's FIXED_CHAR_SEL (0.20 per char) in like_support.c. It is much gentler than PostgreSQL's value, is not derived from data, and is not justified in the code or issue. It sets how fast the estimate falls: 5 chars gives 0.047, 8 chars 0.020, 10 chars 0.011.
- 0.01 floor: an arbitrary clamp that is reached at L>=11 (0.2*0.75^11 ≈ 0.0084). All patterns of 11 or more characters get exactly 1%.
- 64 cap on L (:518): has no effect, because the floor is already reached at L=11.

The q09 literal 'green' (L=5) falls in the steep part of the curve. I found no sign that the constants were chosen to land on a q09 threshold, but nothing was tuned or validated beyond the benchmark either. What happens just outside the window: L=0 gives the old 0.2, and long literals saturate at 1%. Selectivity is never computed from data, so a common long literal such as contains(url,'https://www.') gets 1% even if 100% of rows match. That can cause badly wrong join orders.
- **Outside this benchmark.** Any query on a native DuckDB table (or another scan that supports expression pushdown) with a positive contains/LIKE/prefix/suffix filter on a VARCHAR column against a constant, where the filtered table takes part in a join whose order depends on its estimated size. Examples:
- `SELECT c.name, count(*) FROM orders_log o JOIN customers c ON o.cust_id=c.id WHERE c.email LIKE '%@example.org' GROUP BY 1;`
- `SELECT * FROM events e JOIN pages p ON e.page_id=p.id WHERE contains(p.url, 'checkout') AND e.ts > '2024-01-01';`

Both take the new path: the first is likely rewritten to suffix(), L=12, giving 1%; the second has L=8, giving about 2%.
- **Otherwise.** If the expression is not one of the listed functions, the second argument is not a non-NULL VARCHAR constant, or the first argument is foldable, the helper returns -1. The case then returns the unchanged cardinality (relation_statistics_helper.cpp:477-478), and the existing flat 0.2 default at :147-151 applies exactly as before. Other filter types are untouched.

## E0003: Perfect hash join for RIGHT joins v2 (all 3 gates)

Commit `72de28442d3f`. Files: `src/execution/operator/join/perfect_hash_join_executor.cpp`, `src/execution/operator/join/physical_hash_join.cpp`, `src/include/duckdb/execution/operator/join/perfect_hash_join_executor.hpp`, `src/optimizer/join_filter_pushdown_optimizer.cpp`.
Faster when accepted: q13 1.22×.
Numeric constants in added code: `4194304`.

**Label: heuristic.** The core change is a general, standard technique. It extends direct-addressed (perfect) hash joins to outer joins that preserve the build side, using per-slot match flags written back to the HT. It applies to any RIGHT or flipped-LEFT join on a dense integer key up to 1M, and it includes a real off-by-one fix. The win on this benchmark (q13), however, comes almost entirely from the second limit, MAX_DENSE_BUILD_SIZE = 4M. The author picked it because q13's 1.5M customer key range didn't fit under 1M. They limited it to RIGHT joins only after measuring regressions on q14 and q18 under INNER. The 50% fill factor is principled. But the decision of who gets the large range uses join type as a proxy for "probe is big enough to pay for the serial build" and was tuned against the benchmark's regressions. Upstream would likely accept the RIGHT-join support and might want a cardinality-based gate instead of the 4M constant.

- **Mechanism.** DuckDB's perfect hash join is a direct-addressed array indexed by key minus min. It used to handle only INNER joins, and this change lets RIGHT joins use it too. These are the joins where the build side is preserved, e.g. a LEFT JOIN flipped so the preserved table is the build side. While probing, the engine sets a byte in a per-slot array for each matched build slot. Before the outer scan starts, FlushFoundMatch copies those flags into the regular hash table's found_match field. The existing unmatched-row scan then emits the build rows that never matched, unchanged. NULL build keys are left out of the perfect table but stay in the HT, so they come out as unmatched. The change also adds a second, larger size limit: for build-preserving joins only, a key range up to 4M (instead of 1M) is allowed if the keys fill at least half of it. It also fixes an off-by-one in the duplicate check, so a fully dense key set now qualifies.
- **Trigger.** All of the following must hold:
- The join is INNER or RIGHT, with exactly one equality condition on an integer key: `(op.join_type != JoinType::INNER && op.join_type != JoinType::RIGHT) || op.conditions.size() != 1 || ... != COMPARE_EQUAL || !TypeIsInteger(...)` → bail (perfect_hash_join_executor.cpp:74-75).
- The optimizer now computes min/max aggregates for RIGHT joins: `(join.join_type == JoinType::INNER || join.join_type == JoinType::RIGHT) && join.conditions.size() == 1 && ... COMPARE_EQUAL && TypeIsIntegral(...)` (join_filter_pushdown_optimizer.cpp:275-279).
- The build side has no nested types (perfect_hash_join_executor.cpp:80-89).
- Min and max are not NULL: `if (min.IsNull() || max.IsNull()) return false;` (perfect_hash_join_executor.cpp:92-94).
- Range limits:
  - `build_range > MAX_DENSE_BUILD_SIZE (4194304)` → bail (perfect_hash_join_executor.cpp:115-117).
  - Above `MAX_BUILD_SIZE (1048576)`, the join must propagate the build side and be at least half full: `build_range > MAX_BUILD_SIZE && (!PropagatesBuildSide(op.join_type) || ht.Count() * 2 < build_range + 1)` → bail (perfect_hash_join_executor.cpp:120-123). In practice only RIGHT passes, since the type check above rejects the other build-propagating types.
- No duplicates: `ht.Count() > build_range + 1` → bail (perfect_hash_join_executor.cpp:126). The later full scan of the HT still has to confirm the keys are unique (BuildPerfectHashTable, physical_hash_join.cpp:1008).
- Match tracking runs only when `PropagatesBuildSide(join.join_type)` (perfect_hash_join_executor.cpp:178). The flush happens in `HashJoinGlobalSourceState::Initialize` when `sink.perfect_join_executor` is set (physical_hash_join.cpp:1270-1273).
- **Constants.** - **MAX_BUILD_SIZE = 1048576 (2^20).** This is upstream's existing limit and is unchanged for INNER joins.
- **MAX_DENSE_BUILD_SIZE = 4194304 (2^22).** This is a new, round power of two with no hardware or literature basis. The author says it was chosen so that q13 would take the path: "q13's key range is 1.5M, so with the cap untouched the fast path never fires". At SF10, customer keys span 1–1.5M. Any value from about 1.5M upward would have worked; 4M is arbitrary headroom.
- **Fill factor of 1/2 (`ht.Count() * 2 < build_range + 1`).** This is a principled bound: the array is at most about twice the row count, so memory stays comparable to the regular HT. TPCH customer keys are 100% dense, so it passes easily.
- **What happens just outside the limits:**
  - A RIGHT join with a range between 1M and 4M but under 50% fill uses the regular hash join, as do INNER joins with a range above 1M. Restricting the larger limit to RIGHT joins is itself an empirical patch. When the author allowed it for INNER joins, q14 got 52% slower and q18 13% slower, because the perfect build is serial and turns off the Bloom filter. Those costs apply to large RIGHT joins too, so a RIGHT join with a small probe side and a 1–4M dense build could regress. The author admits this.
  - The boundary is defined by join type, not by build or probe cardinality.
- **The `+1` in the duplicate check** is an off-by-one fix: a range of max−min contains max−min+1 keys. It is general.
- **Outside this benchmark.** Two groups of queries take the new path:
- **Any RIGHT join with a dense, duplicate-free integer key whose range is at most 1M.** This mostly means LEFT JOINs from a small dimension to a larger fact table, which DuckDB flips so the dimension becomes the build side. This part is broad and natural. Example:
  ```sql
  SELECT d.dept_id, d.name, count(e.emp_id) FROM departments d LEFT JOIN employees e ON e.dept_id = d.dept_id GROUP BY ALL;
  ```
  Here `departments` (ids 1..500) is the build side and the join is executed as RIGHT.
- **Ranges of 1M–4M at least half full.** These are RIGHT joins on surrogate-key dimensions of roughly 0.5M–4M rows. Example:
  ```sql
  SELECT u.user_id, count(s.session_id) FROM users u LEFT JOIN sessions s ON s.user_id = u.user_id GROUP BY u.user_id;
  ```
  Here `users` has 2M dense ids. The 4M limit lets this query in, and q13 depends on it.

Neither query is from TPCH.
- **Otherwise.** If the trigger fails, CanDoPerfectHashJoin or BuildPerfectHashTable returns false. `sink.perfect_join_executor.reset()` then runs and the regular parallel hash join is scheduled (physical_hash_join.cpp:1016-1019). Plain INNER joins behave as before, apart from the `+1` duplicate fix and the NULL min/max guard. FlushFoundMatch returns immediately when `slot_found_match` is null (perfect_hash_join_executor.cpp:334-335). The outer SCAN_HT scan is unchanged.

## E0005: Bloom filter on first key of multi-key hash joins

Commit `6709876b091b`. Files: `src/execution/join_hashtable.cpp`, `src/execution/operator/join/physical_hash_join.cpp`.
Faster when accepted: q09 1.22×.

**Label: general.** This is the standard sideways-information-passing Bloom filter, extended from single-key to composite-key equi-joins by filtering on one key, which is a sound pre-filter. It adds no thresholds or shape tests of its own and reuses the engine's existing probe-larger-than-build, build-filtered and runtime-selectivity gates. Nothing refers to particular columns, types or sizes. Choosing key 0 is arbitrary and can be suboptimal, but it is not tuned to this benchmark. The measured benefit is concentrated in one benchmark query (q09), while the code path applies to any filtered composite-key join.

- **Mechanism.** Before this change, DuckDB built and pushed a probe-side Bloom filter only for hash joins with exactly one join condition. Now, when a hash join has several conditions, it builds a Bloom filter on the first equality key alone. The hash table's own hash mixes all equality keys, so it can't be reused for a one-column filter. Instead, at hash-table finalize time the engine gathers key column 0 from the stored build rows, hashes it with the same `VectorOperations::Hash` the probe-side BFTableFilter uses, and inserts those hashes into the filter. The filter is pushed into the probe-side scan only for the column that corresponds to condition 0. Probe rows whose first key has no match on the build side are dropped during the scan, before the join. This is a sound pre-filter: a row that fails key 0 cannot satisfy the full conjunction.
- **Trigger.** The new path only adds to the existing Bloom-filter gate in JoinFilterPushdownInfo::CanUseBloomFilter. All of these must hold:
- a non-perfect hash table: `if (is_perfect_hashtable) { return false; }`
- the condition being pushed is plain equality: `const bool can_use_bf = cmp == ExpressionType::COMPARE_EQUAL;`. Before the change this also required `ht->conditions.size() == 1`; that requirement is removed.
- the build side is filtered: `build_side_has_filter`
- the estimated probe cardinality is larger than the build count: `build_to_probe_ratio > 1.0`
- in FinalizeFilters, the pushdown column is the join's first condition, has no cast, and the build side's min and max differ: `!has_cast && ht && join_condition[filter_idx] == 0 && CanUseBloomFilter(...)`
- the probe column must resolve to a base-table scan column (`probe_info` is not empty).

ReorderConditions puts equality and NOT DISTINCT FROM conditions first, so condition 0 is always an equality key. If it is IS NOT DISTINCT FROM, `cmp` is not COMPARE_EQUAL and no filter is built. In the hash table, multi-key build-time insertion happens when `bloom_filter.IsInitialized() && equality_types.size() > 1`. The old combined-hash insertion is now limited to `equality_types.size() == 1`.
- **Constants.** The change adds no new constants. The only new structural choice is `join_condition[filter_idx] == 0`: the filter always goes on the first equality key in the planner's order, not on the most selective key. That is arbitrary rather than tuned to this workload, and the author lists choosing the most selective key as a follow-up. The thresholds the path inherits were already in the engine and also govern single-key joins:
- `build_to_probe_ratio > 1.0` (the variable is misnamed; it is probe estimate / build count). It is a principled break-even point. Just below it, no Bloom filter is built.
- SelectivityOptionalFilter::BF_THRESHOLD / BF_CHECK_N: the pushed filter switches itself off at runtime if it is not selective enough.
- In-filter and perfect-hash-table limits (also existing) decide when other mechanisms take over instead.

Just outside the trigger, for example when the first key is IS NOT DISTINCT FROM, the build side is unfiltered, or the probe estimate is no larger than the build count, multi-key joins get no Bloom filter, exactly as before.

It was not tuned to the workload. **Label: heuristic.** The technique is principled. A small, selective build side (for example 40 part keys spread over 1..200000) therefore kept the hashed filter and let many false positives through. The change adds a floor to that cap: any range under 2^22 (about 4.2M values, a bitmap of at most 512KB) now gets the exact bitmap, no matter how few keys the build side has. ## E0023: Deliminate selective ANTI delim joins (NOT EXISTS) with simple RHS

Commit `eaec16e1b344`. Files: `src/optimizer/deliminator.cpp`.
Faster when accepted: q22 1.38×.

**Label: general.** This is a principled plan rewrite: correlated anti-join decorrelation that relies on runtime join filters instead of materialising and de-duplicating the delim keys. There are no numeric thresholds and nothing specific to the schema or the data. The gates (one DelimGet, column equality, simple RHS) are natural conditions that a large, ordinary class of NOT EXISTS queries meets.

The NULL semantics are argued soundly: the RHS replacing column is filtered with IS NOT NULL, so NDF and `=` agree on the RHS, and a NULL LHS key matches nothing either way, so ANTI still emits it. The author also says they checked this with NULL-key temp tables; I did not repeat that check.

The main reservations:
- It drops the upstream "keep the delim join when there is a selection" heuristic in favour of relying on Bloom and min/max filters, which plain ANTI joins do not get.
- It was measured on a single benchmark query (q22).

These are trade-off risks, not benchmark-recognition.

- **Mechanism.** DuckDB's Deliminator normally keeps the join between the RHS and the DelimGet when the outer (LHS) side of a delim join has a filter. The reason is that the de-duplicated set of selected outer keys can then shrink the subquery side. Commit E0021 added an exception for SEMI delim joins: if the subquery is "simple" and correlated by plain column equality, the DelimGet join is removed anyway. The delim join then becomes an ordinary comparison join, and its IS NOT DISTINCT FROM conditions are turned into `=` so that runtime min/max and Bloom-filter join filters can reduce the RHS scan. This change applies the same exception to ANTI delim joins, so a correlated NOT EXISTS with a filtered outer query becomes a plain (RIGHT_)ANTI hash join with no DISTINCT and no extra inner join.
- **Trigger.** The path is taken in Deliminator::Optimize when `!candidate.joins.empty() && HasSelection(delim_join) && SelectionIsReplaceableByJoinFilter(candidate)` (src/optimizer/deliminator.cpp:157). HasSelection is true if any LOGICAL_FILTER or any table filter other than IS_NOT_NULL exists under the delim join (deliminator.cpp:214-229). SelectionIsReplaceableByJoinFilter requires all of the following:
- `(delim_join.join_type != JoinType::SEMI && delim_join.join_type != JoinType::ANTI)` returns false, so only SEMI or ANTI pass. ANTI is the only new part (deliminator.cpp:83).
- `candidate.delim_get_count != 1 || candidate.joins.size() != 1` returns false, so there must be exactly one DelimGet and one join with it (deliminator.cpp:84).
- That join is a LOGICAL_COMPARISON_JOIN of type INNER or SEMI (deliminator.cpp:88-93).
- Every one of its conditions is `COMPARE_EQUAL` between two BOUND_COLUMN_REFs (deliminator.cpp:95-100).
- `SubqueryIsSimple(*delim_join.children[1])`: the RHS contains only PROJECTION, FILTER, GET, DELIM_GET and INNER/SEMI comparison joins, so no aggregates, windows or set operations (deliminator.cpp:52-75).

The `=` conversion runs only if all joins were removed and `all_equality_conditions` holds (deliminator.cpp:179-185). It flips an NDF condition only when its RHS column can be traced through projections and filters to a column that the removal made IS NOT NULL (deliminator.cpp:108-134). Data types, cardinalities and table names are never checked.
- **Constants.** There are no numeric thresholds or tuned constants. The gate is structural only: join type is SEMI or ANTI, exactly 1 DelimGet and 1 join with it, column-ref equality conditions, and the SubqueryIsSimple operator whitelist. "Has a selection" is the pre-existing upstream heuristic (any non-IS-NOT-NULL filter; upstream itself carries a TODO about selectivity estimation, deliminator.cpp:215). Just outside the gate, the old behaviour applies:
- correlation by a non-column expression or by `<`;
- a subquery containing an aggregate, window or LEFT join;
- two DelimGets.
In each case the deepest DelimGet join is kept, as upstream does (deliminator.cpp:165-169).
- **Outside this benchmark.** Any correlated NOT EXISTS (and, through the earlier commit, EXISTS) where three things hold: the outer query has some filter, the correlation is column = column, and the subquery is a filter, projection or inner-join tree over base tables. Examples outside TPC-H:

`SELECT c.id FROM customers c WHERE c.signup_date > '2024-01-01' AND NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);`

`SELECT p.sku FROM products p WHERE p.category = 'toys' AND NOT EXISTS (SELECT * FROM returns r JOIN shipments s ON r.ship_id = s.id WHERE s.product_sku = p.sku AND r.reason <> 'damaged');`

Both are common anti-join patterns, such as "customers with no orders" or "products never returned".
- **Otherwise.** If the gate fails, control goes to the unchanged `else if` branch. It removes all DelimGet joins except the deepest one, so the delim join, DISTINCT and duplicate-eliminated scan stay exactly as before (deliminator.cpp:165-169). Delim joins whose LHS has no selection are unaffected; they were already fully deliminated upstream.

One caveat on the new path itself: according to the author's notes, a plain ANTI join (outer side as the build side) gets no runtime join filters. In that orientation the RHS is no longer reduced, either by the delim keys or by a Bloom filter. Whether that is a net loss depends on sizes, and this was not checked.

It applies to any large unique-key integer equi-join and depends on nothing TPC-H-specific. Its thresholds (64k rows, task granularities) only affect performance and look like ordinary engineering values. The part of the change that actually moves the benchmark's q14 is the gate widening: INNER joins with ranges up to 4M at ≥50% density. That 4M cap and the 50% density rule come from an earlier evolve commit, not from upstream DuckDB (which caps at 1M). The cap sits just above the TPC-H dimension key ranges at the benchmark's scale. - **Mechanism.** Two changes to DuckDB's perfect hash join, which is a direct-indexed array keyed by (key − min). Join-filter creation (min/max, Bloom filter) is moved until the duplicate check is done, and a duplicate falls back to the regular hash-join finalize. They are not derived from hardware; the code justifies them only as 'the perfect hash table is not much larger than the regular one'. 4M sits just above the TPC-H build sizes at the benchmark's scale (e.g. part/customer, ~2M dense keys for q14 per the author). - **Outside this benchmark.** Any in-memory INNER or RIGHT equi-join on a single integer key whose build side has unique keys and at least 64k rows benefits from the parallel build. Faster when accepted: q02 1.05×, q07 1.12×, q09 1.13×, q14 1.09×.

**Label: heuristic.** Neither part refers to TPC-H schemas, columns or query shapes.
- Part 2 is a plain, principled decoding micro-optimisation (a fixed word load with a bounds guard) whose constants come from the word size. On its own it would be "general".
- Part 1 is a standard technique: semi-join or sideways information passing via an exact bitmap filter, extended to perfect hash joins. It is gated by a hand-chosen density cut-off (count*4 <= range+1) layered on earlier hand-chosen bitmap-size caps, and the author's gains are concentrated in q07/q02, whose filtered dimension joins (nation-filtered supplier) fit that gate.
- The gate is a natural sparsity condition that many star-schema queries outside TPC-H would meet, so this is not a query-specific branch. But its constants are plausibly tuned rather than derived, hence "heuristic".
- The measured end-to-end evidence is noisy, and the author's own note says the q07-shaped scan CPU did not drop: 2.10s without the BF vs 2.21s with it.

- **Mechanism.** The change has two independent parts.
(1) Join filter pushdown: before this change, a hash join that used a perfect hash table never got a bloom filter, because the engine relied on min/max pruning. Now, when the build keys are sparse within their [min,max] range, the join builds an "exact" bloom filter, which is a bitmap with one bit per key value. It fills the bitmap from the occupied slots of the perfect hash table after the build, then pushes it to the probe-side table scan, so non-matching probe rows are dropped during the scan.
(2) BitPacking compressed scans: when a filtered scan fetches only some rows (sparse selection) from a FOR-mode group of 32- or 64-bit integers, it used to decode each value with a variable-length extract. It now does one fixed 8-byte unaligned load, a shift and a mask. The group pointer and mask are hoisted out of the per-value loop. If the 8-byte load could read past the current group's metadata entry, it falls back to the old extract.

## E0031: Bundle: fallback block reuse cache + large perfect HA v3

Commit `1320822f46f1`. Files: `src/execution/operator/aggregate/physical_perfecthash_aggregate.cpp`, `src/execution/perfect_aggregate_hashtable.cpp`, `src/execution/physical_plan/plan_aggregate.cpp`, `src/include/duckdb/execution/operator/aggregate/physical_perfecthash_aggregate.hpp`, `src/include/duckdb/execution/perfect_aggregate_hashtable.hpp`, `src/include/duckdb/storage/block_allocator.hpp`, `src/storage/block_allocator.cpp`, `src/storage/buffer/buffer_pool.cpp`.
Faster when accepted: q07 1.13×, q08 1.06×, q13 1.36×.

**Label: heuristic.** Extending direct-addressed aggregation to multi-million-slot dense integer domains, with lazy init and a striped parallel merge and scan, is a recognised and broadly useful technique. A per-allocator block free-list is ordinary allocator hygiene. Both apply to many non-TPC-H queries and are on by default. However, the gates look fitted to the workload:
- the 22-bit cap neatly covers custkey-sized domains;
- the DELIM_SCAN exclusion is a shape test;
- the density gate is known to regress sparse, overestimated inputs by 60%;
- the 256MB cache size was picked by benchmarking the q16/q18 regressions that the large HA itself caused. The cache compensates for a benchmark-order side effect rather than following a principled design.
Upstream would plausibly accept the idea with different constants and a cost model, so this is heuristic, not special_case.

- **Mechanism.** Two independent changes. (1) Perfect-hash aggregation, which indexes a direct-addressed array by the bit-packed offsets (value − min) of integer group keys, used to be capped at perfect_ht_threshold bits (default 12, so 4K slots). It now goes up to 22 bits (4M slots) in a "large" mode. In large mode, slot states are initialised only when a slot is first touched (a bool per slot), thread-local tables are merged into the global one in 64K-slot stripes with one lock per stripe, and the output scan runs in parallel over 64K-slot blocks with no order preserved. (2) When the block-allocator pool is off, the BlockAllocator now keeps freed block-size (256KB) buffers on a mutex-protected LIFO stack of at most min(256MB, memory_limit/32) and hands them back on the next block-size allocation, instead of returning them to the malloc implementation. The author says this exists to undo slowdowns in later queries (q14, q16, q18) that appeared once q13 stopped churning 256KB blocks through the radix aggregate.
- **Trigger.** Large perfect HA (planner, plan_aggregate.cpp). All of these must hold:
- every GROUP BY key is an integer type (INT8..UINT64) with min/max statistics, range < 2^31, and the summed bits are `perfect_hash_bits > max_bits` → reject (l.280), where `max_bits = threshold >= LARGE_PERFECT_HT_MIN_THRESHOLD ? - no DISTINCT aggregates, and every aggregate has a combine function (l.287);
- large mode only when `perfect_hash_bits > threshold` (l.292), and then also:
  - `child.estimated_cardinality < slots / 2` → reject (l.152);
  - any aggregate with `HasStateDestructorCallback()` → reject (l.158), which excludes string_agg, list, min/max on strings and similar;
  - `slots * (state_size + 1) * (threads + 1) > max_memory / 8` → reject (l.166);
  - `return !ContainsDelimScan(child)` (l.169).
The default perfect_ht_threshold is "12" (settings.hpp:1340), so with defaults the large mode is on for 13–22-bit key ranges.

Block cache (block_allocator.cpp): in AllocateData, `size == block_size` and `!IsActive() || !IsEnabled()` (l.348). In FreeData, `size == block_size && !IsEnabled()` (l.367) and the cache count is below `MinValue(FALLBACK_CACHE_MAX_BYTES, memory_limit / FALLBACK_CACHE_MEMORY_LIMIT_DIVISOR)/block_size` (l.428, constants at l.98-99). The cache is in effect whenever the block_allocator_memory pool is not configured.
- **Constants.** - LARGE_PERFECT_HT_MAX_BITS = 22 (plan_aggregate.cpp:142): no hardware or literature basis is given. 2^22 = 4M slots, which covers customer-key ranges at the scale factors used (o_custkey at SF10 spans 1.5M, i.e. 21 bits with the +2). One bit more falls back to the radix HT. The issue's earlier title, "dense INNER builds up to 4M range", reuses the same 4M figure.

- Stripe/block size 1<<16 (physical_perfecthash_aggregate.cpp:86): a reasonable granularity, not obviously tuned.

Examples outside TPC-H:

## E0033: Clustered-key radix agg: skip finalize combine for interval-disjoint groups

Commit `a6719babc07a`. Files: `src/execution/radix_partitioned_hashtable.cpp`.
Faster when accepted: q05 1.05×, q18 1.17×.
Numeric constants in added code: `1048576`.

**Label: general.** The technique is principled: skip the parallel combine when runtime checks prove that per-thread groups are key-disjoint. Correctness rests on a checked invariant (disjoint open intervals, with the shared end keys handled separately), not on assumptions about the schema or the query. The constants are either memory caps, the engine's vector size, or existing DuckDB adaptivity thresholds; none look tuned to TPC-H scale. The trigger is a natural data property, clustering on an integer leading group key, that is common in real data loaded in key order.

Caveats:
- It only fires for the first group column and only for integer types.
- It is fragile: one unsorted chunk anywhere disables it globally, and nearly unique clustered keys fall back through lookup-skipping.
- In this benchmark it helps essentially one query (q18).

These limit how far it reaches, but they do not make it a benchmark branch.

- **Mechanism.** In the parallel radix hash aggregate, each thread checks every input chunk to see whether the first group key is non-NULL and non-decreasing. If it is, rows whose key equals the chunk's first or last key go to a small per-thread "boundary" hash table, and the contiguous rows strictly between those keys go to the main hash table. The thread also records each chunk's open key interval. At finalize, if all interior intervals across all threads are pairwise disjoint and no boundary key falls strictly inside any interval, every interior group is known to exist in exactly one thread's table. The main partitions are then marked READY_TO_SCAN with no cross-thread combine, the same way the existing single-thread path works. Only the small boundary partitions go through the normal combine. This exploits physical clustering of the input on the group key and verifies it at runtime, so it does not depend on query shape.
- **Trigger.** Global gate (constructor): `number_of_threads > 1 && !radix_ht.grouping_set.empty()`. The leading group column's physical type must be one of INT8/16/32/64 or UINT8/16/32/64, which sets `clustered_enabled = true`. Any DISTINCT aggregate disables it: `if (aggregate->Cast<BoundAggregateExpression>().IsDistinct()) clustered_enabled = false`.

Per chunk, inside SinkClustered:
- it returns false if `count > STANDARD_VECTOR_SIZE || lstate.intervals.size() >= MAX_CLUSTERED_CHUNKS`;
- it fails on any NULL in key 0 (`!format.validity.RowIsValid(...)) return false`);
- it fails on any decrease (`if (cur < prev) return false`).

Any failure sets the global `any_unclustered = true`, so every thread stops splitting for the rest of the query. The path is also abandoned when adaptive lookup-skipping turns on (`hll_percentage > SKIP_LOOKUP_UNIQUE_PERCENTAGE_THRESHOLD` → `ht.SkipLookups(); ... gstate.any_unclustered = true`), which happens when keys are about 95% unique after 1M sunk rows.

Finalize fast path: `gstate.uncombined_data && !gstate.external && !gstate.any_unclustered && ClusteredIntervalsDisjoint(...)`. That function returns false if `intervals[i-1].second > intervals[i].first` for the sorted intervals, or if any boundary key satisfies `it->first < key && key < it->second`.
- **Constants.** - **MAX_CLUSTERED_CHUNKS = 1048576** (a per-thread chunk cap, line 431). This is a memory bound on the interval and key vectors (about 1M × 2048 rows ≈ 2 billion rows per thread), not a value sized to TPC-H. Above it, the thread falls back and switches the path off globally, so the result is still correct and the cost goes back to the old combine.
- **STANDARD_VECTOR_SIZE**: the engine's vector size. Chunks larger than it are never produced in normal execution.
- **0.95 (SKIP_LOOKUP_UNIQUE_PERCENTAGE_THRESHOLD)** and **1048576 (ADAPTIVITY_THRESHOLD)**: pre-existing DuckDB constants that the patch reuses. Their effect is that a clustered but nearly unique key, such as grouping on a sorted primary key, ends up on the old path.
- **"Number of threads > 1"**: there is nothing to save with one thread, because the existing single_ht path already skips the combine.
- **Integer-only key types**: needed so the order-preserving uint64 encoding works (sign-bit flip for signed types).

None of these values looks tuned to TPC-H sizes. Just outside the gates, a single unsorted or NULL-keyed chunk or an overlap at finalize gives the old full combine, plus the small cost of repartitioning the boundary data.
- **Outside this benchmark.** Any multi-threaded GROUP BY whose first group key is an integer column, where the scanned input arrives (per chunk, and across threads' morsels) in non-decreasing order of that key. This holds for tables loaded or inserted in key order: auto-increment ids, order or line-item style parent–child tables, and time-bucketed integer ids. Groups must have duplicates (not more than 95% unique) and there must be no DISTINCT aggregates.

Examples:
- `SELECT invoice_id, sum(amount), count(*) FROM invoice_lines GROUP BY invoice_id;` where invoice_lines was bulk-loaded ordered by invoice_id.
- `SELECT session_id, min(ts), max(ts), count(*) FROM clickstream GROUP BY session_id HAVING count(*) > 10;` where clickstream was written in session_id order.

These do not qualify:
- a leading VARCHAR, DATE or HUGEINT key;
- input that is unordered, for example after a hash join that reorders the probe side or after a shuffle;
- a GROUP BY where the clustered column is not the first group column.

In TPC-H the beneficiary is essentially q18's `GROUP BY l_orderkey` over lineitem, which is stored in orderkey order.
- **Otherwise.** When the gate fails in the constructor or a thread's first chunk is unsorted, Sink calls `ht.AddChunk(group_chunk, payload_input, filter)` exactly as before. The only cost is one O(n) scan of key 0 per chunk until the first failure, after which the path is off globally.

If splitting ran but the finalize check fails (overlapping intervals, a boundary key inside an interval, a spill, or a later fallback), the boundary data is repartitioned to the main data's radix bits. It is then merged with `uncombined_data.Combine(*gstate.boundary_data)`, and the old full-combine path runs unchanged. The work spent splitting is lost in that case, but results are correct. The external (spilled) case always falls back. The author says this case was not tested.

## E0034: Partition-staged sink for large perfect hash aggregate

Commit `95b3104ecc4a`. Files: `src/execution/operator/aggregate/physical_perfecthash_aggregate.cpp`, `src/execution/perfect_aggregate_hashtable.cpp`, `src/include/duckdb/execution/perfect_aggregate_hashtable.hpp`.
Faster when accepted: q13 1.19×, q14 1.06×.

**Label: general.** This is a textbook technique: partition-buffer the updates to a big table so each flush only touches a cache-sized region, then apply them under per-region locks to one shared table instead of keeping N private copies. It is gated by principled size conditions: more than one 64K-slot stripe, a table over 2 MiB, and fixed-width payloads so rows can be copied. Nothing in the gate refers to TPCH schemas, column names or query shapes. The only tuned value is 4 buffers per stripe, and it affects speed, not which queries qualify.

The caveat is that it only runs inside the "large perfect HA" mode added by earlier evolve commits. That mode's 22-bit cap and density tests were set while targeting this benchmark (q13's o_custkey grouping), so the class of queries that benefit is limited by those older heuristics. Judged on its own, this commit is a general improvement. The author's own numbers show a gain only on q13.

- **Mechanism.** This applies to "large" perfect hash aggregates, the lazily initialised direct-indexed table from earlier commits. In that mode each thread used to scatter every row into its own private table of up to 2^22 slots, and the private tables were merged stripe by stripe at Combine. Now each thread computes slot indices, counting-sorts each input chunk by 2^16-slot stripe, and copies the payload rows into small per-stripe staging buffers (up to 4 × STANDARD_VECTOR_SIZE rows per stripe). When a stripe's buffers are full, the thread takes that stripe's lock and applies them directly to the shared global table, so the private tables are never written and the striped combine is skipped. It is a standard cache-conscious, radix-partitioned buffering technique applied to a shared, lock-striped direct-mapped aggregate table.
- **Trigger.** The new path needs all of the following.

(1) The planner picked a large perfect HA: every group key is an integer type with min/max stats, and the total key bits exceed `perfect_ht_threshold` (default 12) but stay within `LARGE_PERFECT_HT_MAX_BITS = 22` (plan_aggregate.cpp:142,179-183,280,292). `CanUseLargePerfectHashAggregate` must also pass (plan_aggregate.cpp:149-170):
- `child.estimated_cardinality < slots / 2` returns false, so the estimated input must be at least half the slot count;
- no aggregate with `HasStateDestructorCallback()` (no list, string or sorted states);
- `slots * (state_size + 1) * (threads + 1) <= max_memory / 8`;
- no DELIM_SCAN in the child;
- no DISTINCT aggregates and no grouping sets (plan_aggregate.cpp:175,287).

(2) In the HT constructor: `use_staging = total_groups > STAGE_STRIPE_SIZE && data_size + total_groups > STAGE_MIN_TABLE_SIZE`, and every payload type satisfies `TypeIsConstantSize(type.InternalType())` (perfect_aggregate_hashtable.cpp:43-48). That means more than 2^16 slots (17 to 22 key bits) and a table larger than 2 MiB.

(3) Writing straight to the global table happens when `SetStageTarget` returns true, which it does exactly when use_staging holds. It is called on a thread's first Sink (physical_perfecthash_aggregate.cpp:184-192).
- **Constants.** - `STAGE_STRIPE_BITS = 16` (65,536 slots per stripe; perfect_aggregate_hashtable.hpp). ## E0036: Streaming run aggregation for interior rows of clustered-key radix agg

Commit `3c9ef54dba04`. Files: `src/execution/radix_partitioned_hashtable.cpp`.
Faster when accepted: q08 1.06×, q18 1.93×.

**Label: heuristic.** The technique is general and principled: streaming aggregation over sorted runs, which avoids hash probes when the input is already clustered on the group key. The new gates are semantic (FILTER, destructor and combine callbacks, float/nested secondary keys, run-head constancy), not benchmark constants. But it applies only on top of E0033's opportunistic clustered path, which needs per-chunk key ranges that do not overlap across threads. In practice that means base tables physically ordered on an integer key, the layout TPC-H lineitem/orders has on l_orderkey. The early-overlap stop and the serial merge fallback were added specifically to fix a q03 regression. The only measured benefit is q18 (a large GROUP BY l_orderkey over lineitem); every other template was noise. - **Mechanism.** Builds on E0033's clustered-key radix aggregate. That path splits each input chunk whose leading integer GROUP BY key is non-decreasing into boundary runs (the first and last key) and interior rows. Before this change the interior rows still went into the hash table. Now the engine finds the run heads with a linear scan, gives each run of equal keys one aggregate-state block from a per-thread arena, and updates the states directly through a per-row state-pointer vector. If the proof fails, the runs are re-inserted into a SkipLookups HT and combined. A global std::map of streamed intervals stops all streaming as soon as two intervals overlap. This is ordinary chunk compaction at the scan source: it trades one extra copy of the surviving rows for fewer, fuller chunks, so downstream operators (hash probes, aggregates, projections) pay their per-chunk overhead less often. ## E0042: FSST code-level LIKE filter v2: DFA over FSST codes + filter-only no-decode + segment-straddling vectors

Commit `4f25ac98692c`. Files: `src/function/table/table_scan.cpp`, `src/include/duckdb/storage/table/scan_state.hpp`, `src/storage/compression/fsst.cpp`, `src/storage/table/row_group.cpp`, `src/storage/table/scan_state.cpp`, `src/storage/table/standard_column_data.cpp`.
Faster when accepted: q02 1.11×, q13 1.3×, q17 1.07×.
Numeric constants in added code: `127`, `256`.

**Label: general.** I rated this "general". Running a KMP/anchored DFA over dictionary or FSST codes ("compressed pattern matching") is a known, principled technique, and skipping materialisation of filter-only columns is standard late materialisation. The trigger is a broad, natural class: literal-and-% LIKE / contains / prefix / suffix predicates on FSST string columns. It is not keyed to any TPC-H column, pattern or size, and its only numeric constant (127 states) comes from 16-bit table addressing. The limits are real but structural, not tuned:
- NULL-free segments only;
- uniformly FSST columns only;
- filter-only columns only, for the boundary-crossing path.
In TPC-H this fires mainly on q13's `o_comment NOT LIKE '%special%requests%'`, which is where the measured gain is, but the same code serves any log or text filter of the same shape.

- **Mechanism.** Before this change, FSST-compressed string columns had no filter callback, so a pushed-down string filter always decompressed the whole vector and then evaluated the expression. Now, for filters that are LIKE patterns made only of literals and '%' (or contains/prefix/suffix calls), the pattern becomes a byte DFA: a KMP chain per literal part, plus start/end anchors and absorbing done/dead states. For each segment, that DFA is lifted once into a table indexed by (state, FSST code), with extra states for escape-code-plus-literal-byte. It then runs over the compressed codes of the candidate rows, four strings at a time, so no decompression is needed to evaluate the filter. Two related changes:
- If the column is used only by the filter (not projected), no values are produced at all; a constant placeholder is emitted.
- For such filter-only columns, a vector that crosses a segment boundary can now use per-segment filter callbacks piece by piece. Before, it fell back to scan-then-filter.
A new NULL gate also sends segments that may contain NULLs back to the generic path, for every compression type that needs a separate validity pass (RLE included).
- **Trigger.** All of these must hold:
1. The column-level compression has a filter callback (`has_filter = compression && compression->filter`). FSST now registers one (`result.filter = FSSTStorage::Filter;`). Because a column only has a column-level compression when every segment uses the same one, columns that mix compression types fall back.
2. The validity side can be filtered (`validity_has_filter`), and `force_fetch_row` is not set.
3. The table filter is an EXPRESSION_FILTER of the form `[NOT] f(BOUND_REF varchar, BOUND_CONSTANT varchar)`, where:
   - f is one of `contains`, `prefix`, `starts_with`, `suffix`, `ends_with`, `~~` (LIKE) or `!~~` (NOT LIKE);
   - for LIKE, the pattern contains no `'_'` and no `'\\'`;
   - the total literal length plus 3 is at most `MAX_STATES = 127`.
4. The vector is within `STANDARD_VECTOR_SIZE`.
5. The segment's stats say it cannot contain NULLs (`!filter_includes_validity && ...CanHaveNull()` → fallback).
6. If the vector does not scan entirely from one segment (`!scan_entire_vector`), the piecewise path also requires all of the following:
   - `state.filter_only` is set, i.e. the column is not in the scan's `projection_ids` (set via `input.CanRemoveFilterColumns() && !bind_data.is_create_index`);
   - no updates on the column or its validity;
   - every touched segment has a filter callback and no NULLs;
   - validity is covered by a single segment (`SegmentCovers(state.child_states[0], ...)`).
After the filter, the output depends on how the column is used:
- filter-only column: a constant placeholder;
- `EnableFSSTVectorsSetting` is on: an FSST_VECTOR;
- otherwise: only the approved rows are decompressed.
- **Constants.** - `MAX_STATES = 127` (fsst.cpp, `total_length + 3 > MAX_STATES` → return nullptr). This comes from the encoding, not from the workload: the lifted table has 2*states*256 entries addressed by uint16 state offsets (2*127*256 = 65024 < 65536). The +3 covers the done and dead states plus the extra end-anchor state. Just outside it, a pattern whose literals total more than about 124 bytes falls back to decompress-then-evaluate, which is correct, only slower.
- `ALPHABET = 256` is the byte alphabet, and `FSST_ESC` (255) is the FSST escape code. Both are inherent to the format.
- The 4-way interleave is a standard memory-level-parallelism trick and is not a gate.
- `STANDARD_VECTOR_SIZE` is the engine constant.
None of these constants is tuned to TPC-H sizes. The segment size (about 15K rows) and the 13% boundary-crossing figure in the author's notes are facts about the data, not thresholds in the code.
- **Outside this benchmark.** Any table scan with a pushed-down LIKE / NOT LIKE / contains / prefix / suffix filter on a VARCHAR column that is FSST-compressed in all its segments and has no NULLs in the segment. The biggest gain comes when the column is not projected (filter-only). Examples outside TPC-H:
- `SELECT count(*) FROM logs WHERE message NOT LIKE '%timeout%';`
- `SELECT user_id, ts FROM events WHERE url LIKE 'https://shop.%/checkout%';` (url is filter-only here)
- `SELECT id FROM docs WHERE contains(body, 'error') AND starts_with(path, '/var/');`
Not covered: ILIKE (`~~*`), patterns with '_' or escapes, regexes, nullable segments, and columns that mix FSST with dictionary or uncompressed segments (the author notes o_clerk and c_address fall back for this reason).
- **Otherwise.** Unsupported filters take the existing path, unchanged. FSST's Filter calls `StringScan` and then `ColumnSegment::FilterSelection` (`if (!scan_state.has_pattern || vector_count > STANDARD_VECTOR_SIZE)`), and non-FSST columns, projected columns crossing a boundary, and columns with updates take `ColumnData::Filter`. One behaviour change is not a pure fallback: the new NULL gate (`state.current->GetNode().stats.statistics.CanHaveNull()` → `ColumnData::Filter`) sends nullable segments of all compression types that need a separate validity pass (e.g. RLE) to the generic scan+filter path, where before they used their specialised filter. This is a correctness fix, but it may slow down those segments.

## E0045: Leaner streamed-run store for clustered-key radix agg (q18 subquery)

Commit `c9a15ca13231`. Files: `src/execution/radix_partitioned_hashtable.cpp`.
Faster when accepted: q18 1.28×.

**Label: general.** The change is a pure implementation improvement to an existing code path. It merges two run-detection passes into one, removes the data-dependent branches using a standard predicated-compaction idiom, and turns a nested address fill into a flat one. It adds no new gates, constants or shape tests, so any query that already took the clustered or streamed-run path benefits. The gating it inherits (sorted integral leading key, multiple threads) is a natural physical-property condition and belongs to the parent commits. The benefit concentrates on short runs like q18's roughly 4 rows per orderkey, but nothing in the code depends on that.

- **Mechanism.** This rewrites the inner loops of an existing clustered-key radix aggregation path that a parent commit added. That path applies when a sink chunk is sorted on its first GROUP BY key. The rows in the chunk's first and last key runs go to a small boundary hash table. Each interior run of equal keys gets a single aggregate state outside the hash table and is never hashed. Before this change, run detection took two branchy passes over the keys (FindClusteredRuns, then FindRunHeads). Now it takes one branch-free pass: each row writes a candidate head and advances the head count by (cur != prev), records a per-row run id, and ORs together a 'decreasing' flag. The per-row state-address fill changes from a nested loop over runs to a flat states + (run_ids[i]-1)*stride. The routing, the run store, the merge and the semantics are unchanged. This is a standard branch-misprediction removal (predicated compaction) applied to run detection.
- **Trigger.** The diff adds no new conditions. The new code runs whenever the pre-existing clustered path runs, under these gates:
(1) Global gate. The path is enabled only if `number_of_threads > 1 && !radix_ht.grouping_set.empty()` and the first group key's physical type is INT8/16/32/64 or UINT8/16/32/64 (radix_partitioned_hashtable.cpp:251-262). It is disabled if any aggregate `IsDistinct()` (:266-269).
(2) Per-chunk gate. The path is not taken if `count > STANDARD_VECTOR_SIZE || lstate.intervals.size() >= RadixHTLocalSinkState::MAX_CLUSTERED_CHUNKS` (:845). The key must have no NULLs and be non-decreasing within the chunk (`if (!sorted) return false;` :897). Once any thread sees an unsorted chunk, `gstate.any_unclustered` disables the path for all threads (:1049-1057).
(3) Address-fill gate. The changed address fill in SinkInteriorRuns also needs `stream_runs_enabled`. That flag is false if `aggr.filter || aggr.function.HasStateDestructorCallback() || !aggr.function.HasStateCombineCallback()` (:275) or if any later group column is nested, FLOAT or DOUBLE (:279-284). It also needs `first_end < last_start` (:933), i.e. at least 3 runs in the chunk, a successful RegisterRunInterval (:934), and the other group columns changing only at key-run heads (:730-746).
- **Constants.** The diff adds no new thresholds. The run_ids buffer is sized STANDARD_VECTOR_SIZE (:856), which is the engine's vector size and bounds the chunk (checked at :845). heads[n] is written for n <= i < count, so it stays in bounds. The inherited gates come from parent commits: number_of_threads > 1, the integral-key whitelist, and MAX_CLUSTERED_CHUNKS. They are unchanged here, and their tuning belongs to the audits of those commits. Just outside the gates (a non-integral first key, a single thread, an unsorted or NULL-containing key, DISTINCT aggregates), the code takes the ordinary hash-table AddChunk, exactly as before.

Runs are short (a few rows per key), which is where the branch-free form pays off most. Examples:
