## E0001: Sub-row-group scan morsels for tables with few row groups

Commit `fa5fe35db0c1`. Files: `src/include/duckdb/storage/table/row_group_collection.hpp`, `src/storage/data_table.cpp`, `src/storage/table/row_group_collection.cpp`.
Faster when accepted: q02 1.23×.

**Label: general.** This is textbook morsel-driven parallelism: split work finer when there are too few units for the available threads. The trigger is broad and natural ("fewer than about 4 row groups per thread"), it scales with the thread count rather than the data, and the two constants (4 morsels per thread, an 8k-row minimum) are generic round numbers. They are not set to TPCH cardinalities, and nothing tests the schema, operators or plan shape. The TPCH gain comes only from supplier and part happening to be small at this scale factor; any small-table scan with real per-row work benefits the same way. Caveats: the constants are untuned guesses, as the author says. Splitting row groups may add some cost for compressed or FSST segments, from seeking to a vector offset and from repeated per-morsel setup, and that cost was not measured. A row group just under the cutoff may be split into uneven pieces.

- **Mechanism.** Parallel table scans of DuckDB's native storage used to hand out one whole row group (about 122,880 rows) per task, so a table with fewer row groups than threads could keep only a few threads busy. Now the morsel size is computed per scan: about 4 morsels per scheduler thread, at least 4 vectors (8,192 rows), and never more than one row group. When that is smaller than the row group, the scan uses the existing "scan part of a row group from a vector offset" branch, which used to run only under verify_parallelism. DataTable::MaxThreads uses the same formula, so the pipeline starts enough threads to consume the smaller morsels. This is standard morsel-driven over-decomposition, applied to small tables.
- **Trigger.** This runs for every parallel scan of a DataTable's RowGroupCollection, and for transaction-local storage, which goes through the same RowGroupCollection::NextParallelScan (src/storage/local_storage.cpp:405). The morsel size is m = min(max(ceil(total_vectors / (4*T)), 4), row_group_size/2048), from src/storage/table/row_group_collection.cpp:283-288, where T is the scheduler thread count (`TaskScheduler::GetScheduler(context).NumberOfThreads()`, :328) and total_vectors comes from `scan_rows = state.max_row - state.row_groups->GetBaseRowId()` (:327). The sub-row-group branch is taken when `morsel_vectors * STANDARD_VECTOR_SIZE < current_row_group.count || state.vector_index > 0` (:331). With the default row group of 60 vectors this means, in practice, a table with fewer than about 4*T full row groups, i.e. fewer than about T*491k rows (for example under about 3.9M rows at T=8, or about 15.7M at T=32). It is skipped if verify_parallelism is on, which forces m=1 as before (:324-325). The thread-count side uses the same helper at src/storage/data_table.cpp:276-280: `parallel_scan_vector_count = RowGroupCollection::GetParallelScanMorselVectors(GetTotalRows(), row_group_size, threads)`. Nothing in the trigger depends on operators, plan shape, data types, table names or column statistics.
- **Constants.** There are two constants and one input.
- MORSELS_PER_THREAD = 4 (row_group_collection.cpp:281). This is a generic over-decomposition factor for load balancing, the usual round number in morsel-driven schedulers. It sets the cutoff of about 4*T row groups, which scales with hardware threads, not with TPCH table sizes. Just above the cutoff (≥4T full row groups) m reaches 60 and the old whole-row-group path runs. Just below it, m is 59 or similar: nearly whole row groups split into one large piece plus a small leftover piece of one or two vectors. That is slightly wasteful but harmless.
- MIN_MORSEL_VECTORS = 4, i.e. 8,192 rows (:282). This floor stops tiny tables from being split into 2,048-row tasks with high per-task overhead. It is a round number, not obviously derived from TPCH. A 10k-row table gives 2 morsels; a table under 8,192 rows gives one morsel, as before.
- row_group_size/STANDARD_VECTOR_SIZE (:283) is the existing cap, so morsels never span row groups.
None of these values match TPCH table cardinalities. The thing that ties the change to this benchmark is the scale factor: at the benchmarked SF, supplier (100k rows) and part (17 row groups, per the author) fall under the 4*T cutoff. Any small or medium table would fall under it too.
- **Outside this benchmark.** The new path is taken by any parallel scan of a native DuckDB table with fewer than about 4*T row groups: dimension tables, lookup tables and small fact tables. It pays off most when per-row work in the scan pipeline is heavy (expensive filters, LIKE or regex on strings, hash-join probes, aggregation), because then a single 122k-row row group is a real serial bottleneck. Examples, not from TPCH:
(1) `CREATE TABLE users AS SELECT i AS id, md5(i::VARCHAR) AS email FROM range(300000) t(i); SELECT count(*) FROM users WHERE regexp_matches(email, '^ab.*f$');` This is 3 row groups. Before, at most 3 threads did the work; now it is split into roughly 37 morsels of 8 vectors each at T=8.
(2) `SELECT c.country, sum(o.amount) FROM orders o JOIN customers c ON o.cid = c.id GROUP BY 1;` where customers has about 200k rows. The build-side scan of customers now runs on all threads instead of 2.
- **Otherwise.** If the table has enough row groups that m reaches row_group_size/2048 (60), the condition at :331 is false for full row groups. The else branch at :345-350 then runs, which hands out one whole row group, the same as the old code. MaxThreads (data_table.cpp:281-282) then gives the old value too. Under verify_parallelism the old 1-vector morsels are kept, with one difference: processed_rows is now also updated in that mode (:339), which only changes progress reporting. Results stay correct because batch_index is still incremented for each morsel (:352), so order-preserving consumers still see the batches in order. Zone-map and row-group skipping still happens inside InitializeScanInRowGroup (:358-362), but it is now re-evaluated for each morsel instead of once per row group.

## E0006: Rewrite correlated MIN/MAX scalar subquery over a subset of the outer join into a window aggregate

Commit `cef9fd6aec98`. Files: `src/planner/binder/query_node/plan_select_node.cpp`.
Faster when accepted: q02 1.64×.

**Label: general.** This is a published, standard unnesting technique (WinMagic). Every gate is a soundness condition: min/max ignore duplicates, the subquery's scans and conjuncts must be a subset of the outer ones, and correlation must be equality on a column with an exact-equality type. None is a tuned constant or a test on TPC-H names or sizes.

The scope is narrower than the full technique: comma-join trees only, a single subquery, greedy scan matching, and correlation only through an extra table. It always fires, with no cost check. Even so, those limits are conservative engineering choices, not a fingerprint of Q2. Ordinary argmin/argmax-per-group queries on other schemas take the path, although in TPC-H only Q2 benefits.

- **Mechanism.** This is a WinMagic-style rewrite (Zuzarte et al., SIGMOD 2003) done in the binder. Take a WHERE clause whose correlated scalar subquery computes an ungrouped MIN or MAX over tables and conjuncts that also appear in the outer query. The engine no longer decorrelates it with a delim join and hash aggregate. Instead it computes `min/max(arg) OVER (PARTITION BY <correlated outer columns> ROWS UNBOUNDED PRECEDING..UNBOUNDED FOLLOWING)` over the outer join, after filtering on the other WHERE conjuncts, and then evaluates the original conjunct against that window column. This is sound because each partition is the subquery's row set multiplied by the rows of the extra outer tables, and MIN/MAX ignore duplicates.
- **Trigger.** The only call is `rewriter.TryRewrite(condition, root);` (src/planner/binder/query_node/plan_select_node.cpp:389) in Binder::PlanFilter, which is called only for the WHERE clause (:406). Every check below must hold:
(a) Exactly one WHERE conjunct holds a subquery, and only one: `if (subquery_conjunct.IsValid() || count != 1 || !found) return false` (:183). No conjunct is volatile.
(b) The subquery is a correlated scalar subquery: `subquery.subquery_type != SubqueryType::SCALAR || !subquery.IsCorrelated()` (:193). Every correlated column has depth 1 and a type that partitions exactly: `col.depth != 1 || !IsSupportedPartitionType(col.type)` (:197). Allowed types are integral, BOOLEAN, VARCHAR, DATE, TIMESTAMP, DECIMAL and UUID; floats are refused because of -0.0/0.0.
(c) The subquery plan is a chain of single-column projections over one ungrouped aggregate: `!aggr_op.groups.empty() || aggr_op.grouping_sets.size() > 1 ...` (:225). That aggregate is plain min or max: `(aggr.function.name != "min" && aggr.function.name != "max") || aggr.children.size() != 1 || aggr.IsDistinct() || aggr.filter || aggr.order_bys` (:236).
(d) Both the subquery FROM and the outer FROM contain only LOGICAL_GET, LOGICAL_CROSS_PRODUCT and LOGICAL_FILTER, with `default: return false` (:52-64). In practice this means comma-joins; explicit `JOIN ... ON` is refused.
(e) Each subquery scan is matched greedily to a different outer scan of the same table, and neither scan may have table filters, dynamic filters or ordinality: `outer_get.GetTable().get() != table.get() ...` (:267). At least one outer scan must be left unmatched: `if (extra_tables.empty()) return false` (:294).
(f) After remapping, every subquery conjunct equals an outer conjunct (flipped comparisons count as equal). Every unmatched outer conjunct references only the extra tables: `!conjunct_matched[k] && !OnlyReferencesTables(conjunct, extra_tables)` (:330).
(g) Every correlated column belongs to an extra table and appears as a bare column in a matched `=` conjunct: `equality_columns.find(col.binding) == equality_columns.end()` (:338).
- **Constants.** There are no numeric thresholds, cardinality tests or statistics. The fixed choices are all needed for correctness:
- Only min/max, because they ignore duplicates. Rows of the extra tables multiply the subquery's rows inside each partition, which would break count, sum or avg (:236).
- The partition-type whitelist (:197) makes sure grouping is never coarser than SQL equality. Just outside it, a FLOAT or DOUBLE correlation key falls back to the old path.
- The window frame is the whole partition, UNBOUNDED PRECEDING to UNBOUNDED FOLLOWING (:358). That is simply the definition of the rewrite.
- Requiring an equality on each correlated column (:338) rejects NULL keys. Without an equality, for example with `IS NOT DISTINCT FROM`, the query falls back.
There is also no cost gate: whenever the shape matches, the rewrite always fires. It replaces a hash aggregate over the subquery tables with a partitioned window over the full outer join. That could be slower when the outer join is much larger than the subquery's input, but nothing is tuned to TPC-H sizes.
- **Outside this benchmark.** The class is the common "row holding the per-group minimum or maximum" (argmin/argmax) query written with a correlated subquery and comma-joins. The subquery must repeat a subset of the outer tables and predicates and correlate by equality on a column of another outer table. In TPC-H only Q2 matches: Q17 uses avg, and Q15's max subquery is uncorrelated.

Examples outside TPC-H that take the path:
1) `SELECT e.name, d.dname FROM emp e, dept d WHERE e.dept_id = d.id AND e.salary = (SELECT max(e2.salary) FROM emp e2 WHERE e2.dept_id = d.id);`
   Here `emp e2` maps to `emp e`, `dept` is the extra table, and the window is max(e.salary) partitioned by d.id.
2) `SELECT o.id, c.name FROM orders o, customers c, regions r WHERE o.cust_id = c.id AND c.region_id = r.id AND r.name = 'EU' AND o.created_at = (SELECT min(o2.created_at) FROM orders o2 WHERE o2.cust_id = c.id);`
   This returns each EU customer's first order.

Examples that do not take the path:
- The same queries written with `JOIN ... ON`.
- A subquery with its own extra predicate that the outer query lacks, such as `WHERE e2.dept_id = d.id AND e2.active`.
- Correlation through the subquery's own table rather than an extra table, as in the classic `e.salary = (SELECT max(salary) FROM emp e2 WHERE e2.dept_id = e.dept_id)`. Here the outer emp is matched to e2, so no extra table is left and (e) fails at :294.
- **Otherwise.** TryRewrite returns false before changing anything when any check fails. All mutation of `condition` and `root` happens only after the last check (:340 onward). PlanSubqueries and the existing delim-join decorrelation then run unchanged on the original expression (:389-390).
