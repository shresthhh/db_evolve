## E0001: Lower cardinality estimate for substring/LIKE table filters

Commit `c6b5dde53f66`. Files: `src/optimizer/join_order/relation_statistics_helper.cpp`.
Faster when accepted: q09 1.25×.
Numeric constants in added code: `0.05`.

**Label: heuristic.** Giving pattern-match predicates a lower default selectivity than generic range predicates is a standard, schema-independent optimizer heuristic: PostgreSQL has DEFAULT_MATCH_SEL. The trigger is broad and natural, a list of string-matching functions with a constant pattern, and touches no TPC-H tables, columns or query shapes. It would plausibly be accepted upstream. However, the constant 0.05 is unjustified and closely matches the true selectivity of Q9's '%green%' filter, the single query used to validate it. It is applied per scan, ignores what the pattern looks like, and the improvement comes from one plan flip. The constant is plausibly tuned to the workload, and the estimate can make plans worse when patterns are unselective. So this is a heuristic rather than general.

- **Mechanism.** The join-order optimizer guesses how many rows a base-table scan returns after its pushed-down filters. Before this change, any filter that column statistics could not estimate (no equality hit) got one default selectivity of 0.2. Now, if at least one non-optional table filter on the scan is a string pattern match against a constant (contains, LIKE/ILIKE, regexp_matches, suffix/ends_with), the whole scan gets a selectivity of 0.05 instead. This makes such scans look 4x smaller, so they are more likely to be joined early or used as hash-join build sides. Nothing else in the cost model or execution changes.
- **Trigger.** The new path runs only inside RelationStatisticsHelper::ExtractGetStats, for a LogicalGet with non-empty table filters (`if (!get.table_filters.filters.empty())`, src/optimizer/join_order/relation_statistics_helper.cpp:154). Three things must hold:
(a) Some filter has `it.second->filter_type != TableFilterType::OPTIONAL_FILTER` (:176) and `IsStringPatternFilter` returns true for it (:178). That function returns true for an EXPRESSION_FILTER whose expression is a BOUND_FUNCTION with at least two children, where `func.children[1]->GetExpressionClass() == ExpressionClass::BOUND_CONSTANT`, and whose name is one of `"contains" || "like" || "~~" || "ilike" || "~~*" || "like_escape" || "ilike_escape" || "regexp_matches" || "suffix" || "ends_with"` (diff, IsStringPatternFilter). It also returns true for a CONJUNCTION_AND filter that contains such a child, checked recursively.
(b) `bool has_equality_filter = (cardinality_after_filters != base_table_cardinality);` is false (:185). This means the statistics-based InspectTableFilter did not already lower the estimate.
(c) The 0.05 is then applied to the whole table, not per filter: `has_string_pattern_filter ? STRING_PATTERN_SELECTIVITY : DEFAULT_SELECTIVITY` (:187-188). Any other range filters on the same scan add no further reduction.
Cases that do not trigger: `LIKE 'abc%'`, which the optimizer rewrites to `prefix` and which is not in the list. `NOT LIKE` / `!~~`. OR-conjunctions. Patterns that are not constants. In TPC-H this matches Q9 (`p_name like '%green%'`, rewritten to contains) and Q2 (`p_type like '%BRASS'`, rewritten to suffix). It does not match Q14 or Q20 (prefix), or Q13 and Q16 (NOT LIKE).
- **Constants.** There is one constant: `static constexpr double STRING_PATTERN_SELECTIVITY = 0.05;` (diff, next to IsStringPatternFilter). It replaces `DEFAULT_SELECTIVITY = 0.2` (src/include/duckdb/optimizer/join_order/relation_statistics_helper.hpp:57). The value comes from no measurement, statistic or reference. It is a magic default, like many in classic optimizers; PostgreSQL's DEFAULT_MATCH_SEL is 0.005, an order of magnitude lower. It also happens to sit very close to the true selectivity of Q9's `%green%` on p_name (about 5.4%), the one query the author measured. That is reason to suspect it was picked, or at least checked, so that Q9's plan flips. The author says the plan flip needed the part scan estimate (about 2M×0.05 = 100K rows at SF10) to fall below partsupp-derived sizes. A value near 0.2 would leave the old plan, and somewhere between 0.05 and 0.2 lies an unmeasured switching point. Just outside the trigger (a prefix LIKE, NOT LIKE, or a pattern on a column with an equality filter), the old 0.2 or statistics-based estimate applies unchanged. No per-pattern refinement exists (e.g. pattern length, number of wildcards). `'%a%'` and `'%very_specific_token%'` both get 0.05.
- **Outside this benchmark.** Any query whose scan has a pushed-down, constant-pattern contains/LIKE '%x%'/'%x'/ILIKE/regexp_matches/ends_with filter, and no statistics-estimable equality on that scan, then joined to other tables. Examples outside TPC-H:
1) `SELECT u.name, count(*) FROM users u JOIN events e ON e.user_id = u.id WHERE u.email ILIKE '%@example.com' GROUP BY u.name;`
2) `SELECT p.title, sum(s.qty) FROM products p JOIN sales s ON s.product_id = p.id WHERE regexp_matches(p.title, 'wireless') GROUP BY p.title;`
3) `SELECT * FROM logs l JOIN hosts h ON l.host_id = h.id WHERE l.msg LIKE '%timeout%';`
These are common analytic shapes. Whether the new estimate helps depends on the real selectivity. Low-selectivity patterns (e.g. `'%e%'`, `ILIKE '%.com'`) will now be underestimated by 4x more than before. That can put a large side on the build side and make plans worse. The change affects only estimates, so results stay correct.
- **Otherwise.** When no non-optional pattern filter is present, the code takes exactly the old path: `DEFAULT_SELECTIVITY` (0.2) is used, or the estimate from InspectTableFilter when it lowered cardinality (:185-190). There is no other behavioural change. The only extra work is a recursive check of the filter tree during optimization.

## E0002: Bloom filter pushdown for multi-key hash joins on the first key

Commit `0c47211ada63`. Files: `src/execution/join_hashtable.cpp`, `src/execution/operator/join/physical_hash_join.cpp`.
Faster when accepted: q09 1.19×.

**Label: general.** This is a standard extension of sideways information passing: a Bloom filter on one key of a composite equi-join key is a sound, conservative prefilter. Its trigger is broad and has nothing to do with the schema: any multi-key equality join meeting the conditions DuckDB already used for single-key Bloom filters. It adds no thresholds and mentions no columns or tables. Its weakness is that it always picks the first key rather than the most selective one. That is a simplification, not a tuning to this benchmark, and the runtime selectivity check limits the damage when the first key prunes little. The build side does extra work: it gathers and hashes key column 0 once per build row.

- **Mechanism.** DuckDB's hash join already built a Bloom filter over its build-side keys and pushed it into the probe-side table scan (as `col IN BF(...)`), but only for single-key equi-joins. Now multi-key equi-joins get one too, built on the first join key only. In Finalize, the hash table gathers key column 0 from the build rows, hashes it with the same VectorOperations::Hash that the scan-side BFTableFilter uses, and inserts those hashes. It no longer inserts the combined all-keys row hash. The scan can then drop probe rows whose first key matches no build row, before they reach the join. The remaining keys are still checked by the hash join itself.
- **Trigger.** The trigger is the existing single-key Bloom filter trigger with `conditions.size()==1` replaced by a first-key equality test, plus a first-condition gate. In order:
- Not a perfect hash table: `if (is_perfect_hashtable) { return false; }` (physical_hash_join.cpp:769).
- Both the pushed condition and the first hash-table condition are equalities: `cmp == ExpressionType::COMPARE_EQUAL && ht->conditions[0].comparison == ExpressionType::COMPARE_EQUAL` (physical_hash_join.cpp:776-777). This replaces `ht->conditions.size() == 1 && ...`.
- The build side has a filter and the probe side is estimated to be larger than the build: `can_use_bf && build_side_has_filter && probe_larger_then_build` with `build_to_probe_ratio > 1.0` (physical_hash_join.cpp:781-786).
- The filter being pushed belongs to join condition 0: `const bool is_first_condition = join_condition[filter_idx] == 0;` (physical_hash_join.cpp:902).
- There is no type cast between the join key and the scan column: `!has_cast` (physical_hash_join.cpp:899-903).
- The min and max differ (the `else` branch at :864) and the filter target is a pushdown-capable scan column.
- On the build side, the new hashing path runs when `bloom_filter.IsInitialized() && conditions.size() > 1` (join_hashtable.cpp:788). The old row-hash insert is limited to `conditions.size() == 1` (join_hashtable.cpp:720).
- **Constants.** The patch adds no new constants. The ones it relies on already existed:
- `build_to_probe_ratio > 1.0` (physical_hash_join.cpp:783-784). This is the existing cost guard: use the filter only if the estimated probe side is larger than the build side. Just below 1.0, no Bloom filter is pushed and the join runs as before.
- `SelectivityOptionalFilter::BF_THRESHOLD = 0.25f` and `BF_CHECK_N = 75` (selectivity_optional_filter.hpp:52-53). These existing adaptive parameters turn the pushed filter off at runtime if it does not prune enough. This matters more now, because a first-key-only filter is weaker than a full-key one: build-side filtering on the other keys does not shrink it.
- The column index `0`. This is a structural choice (only the first key is used), not a tuned value. Whether the first condition is the selective one depends on the order in which the planner puts the conditions. In this benchmark it happens to be partkey, which is selective. For a join whose first key is unselective (for example a low-cardinality key), the filter costs build time and the runtime selectivity check should switch it off.
- **Outside this benchmark.** Any multi-column equi-join that is not a perfect hash table, where the build side is filtered and smaller than the probe side, the probe side is a table scan on the first key column, and the key types match without a cast. Examples outside this benchmark:
1. Composite-key fact-to-dimension joins: `SELECT sum(s.amount) FROM sales s JOIN promo_items p ON s.item_id = p.item_id AND s.store_id = p.store_id WHERE p.campaign = 'BF2026';`
2. Event joins on tenant and session: `SELECT count(*) FROM events e JOIN sessions x ON e.session_id = x.session_id AND e.tenant_id = x.tenant_id WHERE x.started > DATE '2026-01-01';`
Both previously got min/max filters only. Now the scan of the large table also applies a Bloom filter on item_id or session_id.
- **Otherwise.** When the trigger does not hold, the old path is unchanged:
- Single-key joins still insert the stored row hashes into the Bloom filter via InsertHashes (join_hashtable.cpp:720).
- Multi-key joins where the conditions fail, or where the filter is for a key other than the first, get only the min/max optional filters as before. The Bloom filter is never initialised, so `bf_on_first_key` is false and no extra gather or hash work is done (join_hashtable.cpp:788).
- The Bloom filter is read only by the pushed-down BFTableFilter (physical_hash_join.cpp:795). It is not used inside the hash table, so leaving the combined hash out of it does not affect the join's own probing.
- The pushed filter is wrapped in SelectivityOptionalFilter, which turns it off at runtime if it is not selective enough.
- The author did not test NULL first keys or the external (spilling) hash join.

## E0004: Hash join prefetch v2: build insert + probe, software-pipelined, LLC-sized threshold

Commit `f0d9e1f95179`. Files: `src/execution/join_hashtable.cpp`.
Faster when accepted: q09 1.11×.

**Label: general.** Software prefetching in hash-join build and probe is a standard, well-known technique (see Chen et al., "Improving Hash Join Performance through Prefetching"). Here it applies to every join hash table and has no schema, type or plan-shape tests. The only gate is the pointer-table size, which is a principled test of whether the table fits in cache. Its value (4 MiB, about 262K build rows) and the distance of 16 are untested round numbers, not values fitted to TPCH table sizes. Upstream might retune them per machine. The benefit is clear on large builds; the gain was measured only on q09. The extra non-pipelined prefetch pass over candidate rows and the ungated chain prefetch could cost a little on some workloads, but they never change results.

- **Mechanism.** The hash join now issues software prefetches (__builtin_prefetch) so that cache misses on large hash tables overlap with work instead of stalling one at a time. There are four places. (1) During the probe, the loop over hashes prefetches the pointer-table slot for the key 16 positions ahead. (2) Before the key comparison, a separate loop prefetches every candidate build-row pointer. (3) During the build, the insert loop prefetches for write the slot 16 positions ahead. (4) When following a collision chain, the next row is prefetched as soon as its pointer is loaded. The non-prefetch path is kept as a separate template instantiation. Results cannot change, because prefetches are only hints.
- **Trigger.** Parts 1 to 3 run only when the gate `ShouldPrefetch(ht)` is true: `return ht.capacity * sizeof(ht_entry_t) > HT_PREFETCH_THRESHOLD_BYTES;` (src/execution/join_hashtable.cpp:204-205), where `HT_PREFETCH_THRESHOLD_BYTES = 4ULL * 1024ULL * 1024ULL` (:202). The gate is checked in three places:
- Probe: `if (ShouldPrefetch(ht))` selects `ProbeForPointersInternal<..., true>` (:269). Inside the loop the condition is `if (PREFETCH && i + HT_PREFETCH_DISTANCE < count)` (:216).
- Build-row prefetch before Match: `const bool prefetch = ShouldPrefetch(ht);` (:314), then `PrefetchRead(pointers[state.keys_to_compare_sel.get_index(i)])` (:329).
- Build insert: `const bool prefetch = ShouldPrefetch(ht);` (:688), then `if (prefetch && i + HT_PREFETCH_DISTANCE < remaining_count)` (:694).
Part 4, the chain prefetch in AdvancePointers, has no size gate. It runs whenever `ht.chains_longer_than_one` is true (the early return at :1004) and the loaded next pointer is non-null (`if (ptrs[idx]) { PrefetchRead(ptrs[idx]);` at :1016-1017).
Nothing depends on join type, key types, schema or query shape. It applies to any JoinHashTable, so inner, semi, anti, mark and outer joins with any key types are all covered.
- **Constants.** - **HT_PREFETCH_THRESHOLD_BYTES = 4 MiB** (:202). This is the size of the pointer table (8-byte ht_entry_t), not of the row data. The capacity is `NextPowerOfTwo(count * load_factor)` with `DEFAULT_LOAD_FACTOR = 2.0` (src/include/duckdb/execution/join_hashtable.hpp:408,418). So the gate opens at capacity ≥ 2^20 slots, which means roughly more than 262,144 build rows (more than 2^18). It is a round number meant as "larger than a typical L2 / LLC slice". The code comment says "smaller tables are likely cache-resident" (:201). The author admits no other value was tried. It is not derived from TPCH table sizes, but it also is not calibrated to any machine. Just below it, a build of about 260K rows or fewer runs exactly the old code for parts 1 to 3. Because capacity is a power of two, the gate flips in one step when the build count crosses 2^18.
- **HT_PREFETCH_DISTANCE = 16** (:200). This is a conventional software-pipelining distance, and the author tested no alternative. Near the end of a vector the condition `i + 16 < count` skips the prefetch, so the last 16 iterations of each vector (up to 2048 rows) get no prefetch. This is harmless.
- The `__builtin_prefetch(p, 0/1, 3)` hints request read or write with high temporal locality (:187-197). These are the standard defaults.
- **Outside this benchmark.** Any hash join whose build side is larger than about 262K rows, so that the pointer table exceeds 4 MiB, on any schema and with any key types. Part 4 also applies to any build with duplicate keys or hash collisions, whatever its size. Two examples outside TPCH:
1. `SELECT u.country, count(*) FROM events e JOIN users u ON e.user_id = u.id GROUP BY 1;` with users at 5M rows and events at 100M rows. Both build and probe prefetch.
2. `SELECT o.id FROM orders_2024 o WHERE o.sku IN (SELECT sku FROM inventory_snapshot);` with a 1M-row inventory. This is a semi join over the same JoinHashTable. If inventory has duplicate skus, the chain prefetch also fires.
- **Otherwise.** When the gate is false, ProbeForPointers dispatches to the `<USE_SALTS, HAS_SEL, false>` instantiation (:278-282). That is the same code as before, because `PREFETCH && ...` is a compile-time false. The insert and row-pointer loops skip their prefetch branches through the runtime `prefetch` bool (:314, :688). So the old behaviour is unchanged, except for one predictable branch per iteration. The one change that is not gated is the AdvancePointers chain prefetch (:1017). It now runs on small tables too, where it is probably a no-op or a tiny cost.
