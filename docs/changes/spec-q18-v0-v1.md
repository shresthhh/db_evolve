## E0005: Zonemap-prunable join key-set filter through compressed-materialization projections

Commit `774cbe3fcc2b`. Files: `src/execution/operator/join/physical_hash_join.cpp`, `src/include/duckdb/execution/operator/join/join_filter_pushdown.hpp`, `src/optimizer/join_filter_pushdown_optimizer.cpp`.
Faster when accepted: q18 1.11×.

**Label: heuristic.** Part (A) is a principled generalization. It removes a blind spot where compressed materialization's `x - min` projection blocked join-filter pushdown, and it is gated only by type conditions.

Part (B) is a standard idea: a range-set or zonemap filter built from the build keys by greedy largest-gap splitting. It contains nothing tied to TPCH's schema or query text. Its gate, however, is an ad-hoc constant (64× a reused threshold of 50, so 3200 build rows), it reuses the IN-list setting as a range budget, and it only pays off on probe tables clustered on the key, as lineitem and orders are on orderkey. It would plausibly be accepted upstream with its own setting and better-justified limits, so the overall label is "heuristic" rather than "general".

- **Mechanism.** When a hash join finishes its build side, DuckDB can push a filter built from the build keys into the probe-side table scan. That filter is used only for zonemap (row-group min/max) pruning. The change widens this in two ways.

(A) The pushdown used to stop when the probe key was wrapped in compressed materialization's `__internal_compress_integral_*(x, min)` projection, which computes `x - min`. It now passes through that projection, records `min` as `storage_offset`, and adds the offset back to every key (in HUGEINT, with an overflow check) before casting to the storage type. This applies to both the min/max filters and the IN filter. The bloom filter is turned off whenever an offset is present.

(B) Before, the IN-list zonemap filter was built only when the build side had at most `dynamic_or_filter_threshold` (default 50) rows. Now the keys are scanned when the build side has up to 64×threshold rows. If there are at most threshold distinct keys after the cast, the old IN filter is produced. If there are more and the storage type is integral, the sorted distinct keys are split at the threshold−1 largest gaps. The result is pushed as an `OptionalFilter` (zonemap pruning only, never row filtering) holding an OR of at most `threshold` ranges `[lo,hi]`, with a single-key range becoming an equality.
- **Trigger.** (A) The optimizer walks the probe expression. The new step is taken for a BOUND_FUNCTION when `StringUtil::StartsWith(func.function.name, "__internal_compress_integral_")`, `func.children.size() == 2`, no offset has been recorded yet (`!filter.storage_offset.IsNull()` → reject), `func.children[1]` is a BOUND_CONSTANT that is not NULL, and both input and output are integral with an input of at most 64 bits (`GetTypeIdSize(src.InternalType()) > GetTypeIdSize(PhysicalType::INT64)` → reject). The walk then continues into the child, which must still reach a LogicalGet column (src/optimizer/join_filter_pushdown_optimizer.cpp:55-75). Through a UNION the offset is copied to each child (line 130). At run time a key is dropped from the filter if the HUGEINT add overflows or the try-cast to the storage type fails (physical_hash_join.cpp:717-735).

(B) `CanUseInFilter` (physical_hash_join.cpp:740-749) needs `ht->Count() > 1`, an equality join (`cmp == COMPARE_EQUAL`), and `(ht->Count()+63)/64 <= dynamic_or_filter_threshold`, i.e. at most 3200 build rows (rows, not distinct keys). `PushInFilter` still bails out if the key list contains NULL or the keys form a dense range (line 779, `ContainsNull || IsDenseRange`). If the number of distinct keys is `<= max_filter_count`, an IN filter is built as before (line 785). Otherwise ranges are built only when `max_filter_count >= 2`, `storage_type.IsIntegral()`, the type is not UHUGEINT, and `in_list[0].type() == storage_type` (line 792). Every range endpoint must cast back to the storage type (line 825). The result is always wrapped as `make_uniq<OptionalFilter>` (line 845).
- **Constants.** `dynamic_or_filter_threshold` = 50 (src/common/settings.json:452-456, `"default_value": "50"`) is an existing DuckDB setting and is not changed. It is reused here for a second purpose, as the maximum number of ranges. That choice is convenient, not derived; the author notes "That would need its own constant".

`JOIN_FILTER_RANGE_SET_FACTOR = 64` (physical_hash_join.cpp:738) is a round power of two with no stated derivation beyond "so that scanning the keys stays cheap". Together they cap the build side at 3200 rows. On q18 the build side is roughly 100 keys (author: "about 111 keys"), so any factor of 3 or more would have triggered. The constant is not finely fitted to q18, but nothing measured supports 64 either.

Just outside the cap (3201 or more build rows, counting duplicates) no IN or range filter is pushed at all. Only the min/max filter and possibly the bloom filter remain, which is the old behaviour. With exactly threshold+1 distinct keys the result is 50 ranges, at least one of them covering 2 keys. Choosing the largest gaps is a standard greedy that is optimal for minimising the total covered span with k intervals, not a workload-specific rule.

Part (A) has no tuned constants; its only limits are the ≤64-bit integral input and a single offset.
- **Outside this benchmark.** (A) Any join whose probe key is an integer column that compressed materialization rewrites into `x - min` (it does this when statistics show a narrow range and it materializes through an ORDER BY, aggregate or join). Such joins now get min/max and IN zonemap filters at all, where before they got none.

(B) Any equality hash join with an integral probe key and between threshold+1 distinct keys and 3200 build rows, where the keys are not dense. The pruning only pays off when the probe table is physically clustered on the join key, so that row-group zonemaps are narrow; on unclustered data the ranges prune nothing and the only cost is building them.

Examples outside TPCH:
- `SELECT e.* FROM events e JOIN (SELECT session_id FROM sessions WHERE flagged GROUP BY session_id HAVING count(*) > 5) s ON e.session_id = s.session_id;` with `events` loaded in `session_id` order and a few hundred flagged sessions.
- `SELECT l.* FROM log_rows l WHERE l.batch_id IN (SELECT batch_id FROM batches WHERE status = 'failed' ORDER BY batch_id);` with `log_rows` appended in `batch_id` order and 50 to 3000 failed batches.
- **Otherwise.** If (A)'s conditions fail, the optimizer returns false as before and no join filter is pushed for that column. Columns without an offset go through `CastJoinFilterValueToStorage`, which then does exactly the old `DefaultTryCastAs(storage_type)`, so behaviour is unchanged.

For (B), builds with more than 3200 rows, non-equality joins, NULL or dense keys, and non-integral or UHUGEINT storage push no IN or range filter. That is the same result as before for all sizes above 50, except that non-integral keys between 51 and 3200 rows are now scanned before the bail-out, which is wasted work. Builds with at most 50 distinct keys get the old IN filter.

One behaviour change also covers previously handled cases: the bloom filter is skipped whenever an offset is present. Before, such columns got no pushdown at all, so this loses nothing compared with the old code. Since every new filter is optional (zonemap only), results cannot change; only pruning differs.

## E0006: Extra selectivity for HAVING-style aggregate-result range filters in join ordering

Commit `d6c752b412f9`. Files: `src/optimizer/join_order/cardinality_estimator.cpp`, `src/optimizer/join_order/relation_manager.cpp`.
Faster when accepted: q18 1.09×.

**Label: heuristic.** The SEMI-join change is a principled, broadly applicable containment estimate (|L|·|R|/tdom, with the old constant kept as a cap). On its own it would be "general". It has caveats: |RHS| is a product of relation cardinalities rather than a distinct count of the RHS key, and duplicate RHS keys make it underestimate how much the RHS filters. But the plan flip that produced the speedup also needs change 1. That change adds a second, unconditional 0.2 factor to any aggregate under a range HAVING, a pure prior with no use of statistics or of the constant's value. It is broad in shape and not tied to TPCH's schema, but it is a magic-number nudge that happens to push q18's subquery estimate past the 1/5 crossover. It is plausibly upstreamable with different constants or a stats-based version, so it is not a special case, but it is not a principled improvement either.

- **Mechanism.** There are two cardinality-estimate changes in the join-order optimizer. (1) Before this change, an aggregate relation with any filter above it already had its estimate scaled by 0.2. Now, if one of those filters is a range comparison (<, <=, >, >=) between an aggregate output column and a constant (e.g. HAVING sum(x) > c), the estimate is scaled by 0.2 a second time, so 0.04 overall. (2) For SEMI joins, the denominator multiplier was a fixed 5. It is now max(5, tdom / |RHS|), where tdom is the join key's distinct count and |RHS| is the product of the estimated cardinalities of the relations on the right side. This is the textbook containment estimate: the output is roughly |LHS| * |RHS| / tdom when the RHS holds few distinct keys. The fixed factor of 5 is still the ceiling on the estimate. Together, a semi join against a small, HAVING-filtered subquery is now estimated as small, so the optimizer can put it on the build side.
- **Trigger.** Change 1 (relation_manager.cpp): the relation must be a LOGICAL_AGGREGATE_AND_GROUP_BY extracted as a join-order relation with non-empty datasource filters (`if (!datasource_filters.empty())`, relation_manager.cpp:317). At least one filter expression, or a child of a nested AND, must be a BOUND_COMPARISON of type `COMPARE_GREATERTHAN/…GREATERTHANOREQUALTO/…LESSTHAN/…LESSTHANOREQUALTO` (relation_manager.cpp:220-224). One side must be a bare BOUND_COLUMN_REF with `binding.table_index == aggregate_index`, so an aggregate result and not a group key. The other side must be `IsFoldable()` (relation_manager.cpp:229-234). Casts, arithmetic over the aggregate, OR, equality and BETWEEN-as-non-comparison do not match. When it matches: `cardinality * DEFAULT_SELECTIVITY`, floored at 1 (relation_manager.cpp:321-326). Change 2 (cardinality_estimator.cpp:266-275): `join_type == JoinType::SEMI && right_set`, then `tdom > 0 && rhs_cardinality >= 1 && rhs_cardinality < tdom`, giving `selectivity = MaxValue(selectivity, tdom / rhs_cardinality)`. Here rhs_cardinality = GetNumerator(right_set) = the product of per-relation `stats.cardinality` (cardinality_estimator.cpp:132-139, 464-467), which for an aggregate already includes the filter discounts. ANTI joins, MARK joins and delim joins are not affected.
- **Constants.** DEFAULT_SELECTIVITY = 0.2 (relation_statistics_helper.hpp:57) is DuckDB's existing generic filter-selectivity guess. Applying it a second time is an arbitrary "HAVING range filters are very selective" prior with no data behind it: a HAVING count(*) > 0 or sum(x) > -1 that keeps every group gets the same 0.04 factor. There is no threshold. Any foldable bound qualifies, regardless of its value relative to the aggregate's stats. DEFAULT_SEMI_ANTI_SELECTIVITY = 5 (cardinality_estimator.hpp:92) is pre-existing and is kept as a lower bound on the divisor via MaxValue. The new branch changes things only when tdom/|RHS| > 5, i.e. the RHS has fewer than 20% as many rows as the key domain. Just outside that (|RHS| ≥ tdom/5), the old estimate holds exactly, so the change is continuous at the boundary. The `rhs_cardinality < tdom` guard is redundant given the max with 5. Neither constant was tuned to TPCH sizes. The trigger for the plan flip in q18 is that 0.2*0.2 applied to a ~1.5M-group aggregate gives an RHS small enough that tdom/|RHS| beats 5. That depends on the double-0.2 prior, not on a measured selectivity.
- **Outside this benchmark.** Change 2 covers any IN / EXISTS subquery that becomes a SEMI join where the subquery side is estimated well below the key's distinct count. That is common: e.g. `SELECT * FROM events e WHERE e.user_id IN (SELECT user_id FROM users WHERE country = 'NZ')`, or `SELECT * FROM posts p WHERE EXISTS (SELECT 1 FROM flagged f WHERE f.post_id = p.id)` with a small flagged table. Change 1 covers any aggregate subquery with a range HAVING used in a join or semi join, e.g. `SELECT o.* FROM orders_log o WHERE o.session_id IN (SELECT session_id FROM clicks GROUP BY session_id HAVING count(*) >= 50)`, or `SELECT c.name, t.total FROM customers c JOIN (SELECT cust_id, sum(amount) AS total FROM payments GROUP BY cust_id HAVING sum(amount) > 10000) t ON c.id = t.cust_id`. Both are natural shapes in analytics workloads. In TPCH, q18 is the clear beneficiary.
- **Otherwise.** If the aggregate's filters contain no matching range comparison, the estimate is the original single 0.2 discount, unchanged. For ANTI joins, or SEMI joins where tdom/|RHS| ≤ 5 (or tdom is 0, or the RHS estimate is < 1), selectivity stays DEFAULT_SEMI_ANTI_SELECTIVITY = 5, exactly the old code. Delim-join semi estimates (relation_manager.cpp:543-547) still use the fixed 5. Only estimates change, never execution semantics, so a wrong guess can only produce a worse join order, not a wrong result.
