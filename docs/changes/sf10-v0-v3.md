## E0008: Contains-filter scan selectivity to flip q09 build sides at SF10

Commit `f3239195db92`. Files: `src/optimizer/join_order/relation_statistics_helper.cpp`.
Faster when accepted: q09 1.61×.
Alone on v0: 1.016× over all templates; faster q03 1.09×, q09 1.58×; slower q10 0.92×.
Numeric constants in added code: `0.2`.

**Label: heuristic.** The idea is principled and general in kind: give substring-containment predicates a lower default selectivity than the generic 20%. It is purely an estimate change, it is not tied to TPCH table or column names, and it fires for any single-substring LIKE or contains() with a literal of 3 or more bytes. That is a broad, natural class. However, both constants (×0.2 giving 0.04, and the 3-byte minimum) are hand-picked and unvalidated. 0.04 lands close to the real selectivity of '%green%' in TPCH, and it was chosen after the previous attempt at SF1 failed to flip q09's plan. In this benchmark the rule fires only for q09. Upstream would plausibly accept something like it, perhaps with a different constant or a length-scaled model. It is a default-selectivity heuristic tuned to flip one benchmark plan, not a statistics-based estimate.

- **Mechanism.** When the join-order optimizer estimates a base table scan's cardinality and finds no equality-filter estimate from statistics, it normally assumes the pushed-down filters keep 20% of rows (DEFAULT_SELECTIVITY = 0.2). With this change, if any non-optional pushed-down filter on that scan is `contains(col, '<literal of at least 3 bytes>')`, or an AND that includes one, it assumes 4% (0.2 × 0.2) instead. Only the cardinality estimate changes. Execution is unchanged, but the lower estimate can change the join order and which side builds the hash table. In q09 it shrinks the `part` estimate about 5×, which flips the build sides.
- **Trigger.** All of the following must hold, all inside RelationStatisticsHelper::ExtractGetStats for a LogicalGet:
(1) The scan has pushed-down table filters: `if (!get.table_filters.filters.empty())` (relation_statistics_helper.cpp:158).
(2) At least one of those filters is not an OPTIONAL_FILTER and `IsContainsFilter(*it.second)` returns true (:180-184).
(3) IsContainsFilter matches only an EXPRESSION_FILTER whose expression is a BOUND_FUNCTION with `func.function.name != "contains" || func.children.size() != 2` false (:75). The second child must be a BOUND_CONSTANT (:79). It must be a non-NULL VARCHAR, `value.IsNull() || value.type().id() != LogicalTypeId::VARCHAR` (:83), and `StringValue::Get(value).size() >= CONTAINS_MIN_LITERAL_LENGTH` (:86, constant = 3 bytes). It also recurses into CONJUNCTION_AND children. It does not look inside NOT, OR, or any other wrapper. So `NOT LIKE '%x%'` (which becomes NOT(contains)) and multi-wildcard LIKE patterns are not matched.
(4) Statistics produced no equality-based reduction: `bool has_equality_filter = (cardinality_after_filters != base_table_cardinality); if (!has_equality_filter && has_non_optional_filters)` (:189-190).
`col LIKE '%abc%'` is rewritten to contains() by like_optimizations.cpp:135-137 ("Contains LIKE pattern: [%]+[^%_]*[%]+"), so the usual SQL spelling triggers it too. If this rewrite runs after filter pushdown, the expression is already `contains`. In TPCH only q09 (`p_name LIKE '%green%'`) meets this. q13's '%special%requests%' is not a single-substring pattern, and q16's NOT LIKE is wrapped in NOT.
- **Constants.** CONTAINS_SELECTIVITY = DEFAULT_SELECTIVITY * 0.2 = 0.04 (:64), "Substring containment filters with a non-trivial literal are typically far more selective than other filters". The 0.2 multiplier comes from no model, paper or measurement; it is a hand-picked factor. Coincidentally, the true selectivity of '%green%' on TPCH p_name is about 5%: 5 words drawn from 92 colours. So 0.04 sits close to this workload's actual value, and it is exactly enough to flip q09's build sides at SF10. The author's notes say 0.2 alone did not flip the plan at SF1 (E0002). The constant is not tied to string length, column statistics or data. A needle that matches 90% of rows gets the same 4%, and the larger misestimate could pick a bad build side.
CONTAINS_MIN_LITERAL_LENGTH = 3 bytes (:65). This is an arbitrary guard against short, common needles. With a 2-byte needle such as contains(x,'ab') or LIKE '%ab%', the estimate falls back to 20%. The length is counted in bytes, so a single 3-byte UTF-8 character qualifies.
The trigger is a step: one qualifying filter anywhere in an AND, or on any column, switches the whole scan from 0.2 to 0.04. Several such filters do not compound.
- **Outside this benchmark.** Any scan with a selective substring predicate (single-substring LIKE '%…%' or contains()) whose literal is at least 3 bytes, where no equality filter already reduced the estimate, and which takes part in a join whose order or build side depends on that scan's estimate. This is a common pattern in log, product and text search. Examples outside TPCH:
`SELECT u.name, count(*) FROM events e JOIN users u ON e.user_id = u.id WHERE u.email LIKE '%@example.org%' GROUP BY u.name;`
`SELECT p.title, sum(s.qty) FROM sales s JOIN products p ON s.product_id = p.id JOIN stores st ON s.store_id = st.id WHERE contains(p.description, 'waterproof') AND p.price > 10 GROUP BY p.title;`
Both would get a 4% estimate for the filtered dimension instead of 20%, making it more likely to be the build side.
- **Otherwise.** If no qualifying contains filter is present, the code computes exactly the old value: `has_contains_filter ? CONTAINS_SELECTIVITY : RelationStatisticsHelper::DEFAULT_SELECTIVITY` (:191-194) reduces to the original `base * DEFAULT_SELECTIVITY` with a floor of 1. If an equality filter already lowered the estimate, the contains flag is ignored. Execution operators are not touched.

## E0009: Per-key bloom filter for multi-key joins, revived for the post-E0008 q09 plan

Commit `448b47834be5`. Files: `src/execution/join_hashtable.cpp`, `src/execution/operator/join/physical_hash_join.cpp`, `src/include/duckdb/execution/join_hashtable.hpp`, `src/include/duckdb/execution/operator/join/join_filter_pushdown.hpp`.
Faster when accepted: q05 1.06×, q09 1.27×.
Alone on v0: 1.003× over all templates; faster q03 1.09×, q20 1.05×; slower q02 0.95×.

**Label: general.** This extends an existing standard technique, sideways information passing through runtime bloom filters, from single-key to multi-key equi-joins. Each per-key filter is a necessary condition for a match, so it is semantically sound. NULL handling follows each condition (`NullValuesAreEqual(cond_idx)`). The build-side hash matches the probe-side hash: both use VectorOperations::Hash, per bloom_filter.cpp:90-92. The gates are the same broad gates DuckDB already used for single-key filters, plus a non-nested-type test. Nothing refers to the TPC-H schema, its data sizes or a particular query shape. The only new constant is the cap MAX_KEY_BLOOM_FILTERS = 2. It is arbitrary, but it is a cost bound, not a selectivity tuned to q09. Two caveats keep this from being a clean "general": the build side pays the gather and hash cost even for unselective keys, and there is no cost model choosing which keys deserve a filter. Upstream reviewers might ask for that, but the change is general in kind and in trigger.

- **Mechanism.** Before this change, DuckDB's hash join pushed a runtime bloom filter into the probe-side scan only for single-key equality joins. The filter was filled from the row hash of the hash table. Now a multi-key equi-join can build a separate bloom filter for each equality key. While the hash table is finalized, it gathers that key column from the build rows, hashes it on its own with VectorOperations::Hash (the same function the probe-side BFTableFilter uses), and fills the filter. After the build completes, the filter is pushed into the probe table scan as a single-column `col IN BF(...)` filter. Each per-key filter is a necessary condition for a match, so probe rows are pruned early, before the multi-key hash probe. Each filter is still wrapped in the existing SelectivityOptionalFilter, which switches off at runtime if it does not filter enough.
- **Trigger.** All of the following must hold, per key, in FinalizeFilters and CanUseBloomFilter (src/execution/operator/join/physical_hash_join.cpp):
(1) The existing join-filter-pushdown machinery already found a probe-side table scan column for the join condition, and the column needs no cast: `bool has_cast = condition_type != pushdown_column.storage_type;` and `if (!has_cast && ht && deferred_bloom_filters && CanUseBloomFilter(...))` (physical_hash_join.cpp:910-913).
(2) The join does not use a perfect hash table: `if (is_perfect_hashtable) { return false; }` (:770).
(3) The hash table conditions match the operator conditions: `ht->conditions.size() != op.conditions.size()` returns false (:777).
(4) The key is an equality condition: `condition.comparison == ExpressionType::COMPARE_EQUAL` (:781).
(5) New for multi-key joins: the key type is not nested, and the join has fewer than 2 per-key filters so far: `!condition.left->return_type.IsNested() && (ht->HasBloomFilter(cond_idx) || ht->BloomFilterCount() < MAX_KEY_BLOOM_FILTERS)` with `MAX_KEY_BLOOM_FILTERS = 2` (:784-786).
(6) Unchanged pre-existing gates: the build side has a filter (`build_side_has_filter`, set from `IsFiltering(join.children[...])` in join_filter_pushdown_optimizer.cpp:305/307), and the estimated probe cardinality is larger than the build count, `build_to_probe_ratio > 1.0` (:791-796).
At build time, the per-key filling runs only when `conditions.size() > 1` (join_hashtable.cpp:816-836). Single-key joins keep the old path: `conditions.size() == 1 && HasBloomFilter(0)` (join_hashtable.cpp:747).
- **Constants.** MAX_KEY_BLOOM_FILTERS = 2 (physical_hash_join.cpp:784). This is a budget the author picked to cap extra build-side work. It is not derived from hardware or from the literature. It happens to equal the number of keys in the q09 partsupp join (ps_partkey, ps_suppkey), so every 2-key join gets a filter on both keys. With 3 or more keys, only the first two pushable keys (in condition/probe-info order) get a filter, and the rest get none. It is an arbitrary cap, not a tuned value: q09 would behave the same with any cap of 2 or more. The other constants are pre-existing and unchanged: ratio > 1.0 (:793), and the SelectivityOptionalFilter values BF_THRESHOLD = 0.25 and BF_CHECK_N = 75 (selectivity_optional_filter.hpp:52-53). The runtime selectivity check means a filter on an unselective key (for example l_suppkey in q09) should disable itself, but the author did not measure whether it does.
- **Outside this benchmark.** Any multi-column equi-join that meets all of these conditions:
- the build side is filtered;
- the build side is smaller than the probe side;
- at least one key column of a probe-side base-table scan is selective given the build-side filter;
- the join does not use a perfect hash table.
This is common with composite foreign keys, as in fact tables joined to bridge or snapshot tables. Examples outside TPC-H:
1) `SELECT s.* FROM sales s JOIN store_promotions p ON s.store_id = p.store_id AND s.product_id = p.product_id WHERE p.promo_type = 'CLEARANCE';` Here sales is scanned with `store_id IN BF` and `product_id IN BF`.
2) `SELECT e.user_id, count(*) FROM events e JOIN experiments x ON e.user_id = x.user_id AND e.variant = x.variant WHERE x.experiment_name = 'checkout_v2' GROUP BY 1;` Here x is the small filtered build and events is the large probe.
The new path is not tied to TPC-H tables, columns or types. Only the 2-filter cap matters, and only for joins with 3 or more keys.
- **Otherwise.** If any per-key gate fails, that key gets no bloom filter, and the existing min/max dynamic filters are still pushed as before (physical_hash_join.cpp:880-907). Single-key joins follow the same logic as before: the filter is filled from the row hash in InsertHashes (join_hashtable.cpp:747). One change applies to them too: the old code called SetBuildBloomFilter(true) both when deferring and when pushing. The new code requests the filter only in the deferred branch and only when deferred_bloom_filters is non-null (:912). Multi-key joins that fail the gates behave exactly as before: no filter is built and Finalize adds no extra work, because key_bf_conditions is empty. When a filter is built but turns out unselective, the SelectivityOptionalFilter disables it at runtime. The extra build-side gather and hash cost is still paid.

## E0010: Derive per-table OR filters when the OR sits under a root AND (JoinDependentFilterRule after distributivity)

Commit `7ba03a07c16a`. Files: `src/optimizer/rule/join_dependent_filter.cpp`.
Faster when accepted: q14 1.05×, q19 1.79×.
Alone on v0: 1.029× over all templates; faster q03 1.09×, q19 2.0×; slower q02 0.93×.

**Label: general.** The change extends an existing, sound predicate-derivation rewrite (deriving single-table filters implied by an OR of ANDs) to the shape the engine's own DistributivityRule produces. Without it, the rule was effectively turned off for any OR that shared a common factor, a gap between two engine rules rather than anything benchmark-specific. The trigger is purely structural (an OR child of the root AND, join-dependent branches) with no constants, statistics, or schema- or type-specific tests, and the derived predicates are logically implied by the original one, so results stay correct. In TPC-H it pays off mainly on q19, but the shape is common in real-world SQL. Remaining caveats: only direct OR children are handled, and termination relies on Equals()-based deduplication.

- **Mechanism.** JoinDependentFilterRule is an existing DuckDB expression-rewriter rule. Given a filter `(A1 AND B1) OR (A2 AND B2) ...` where the branches touch several tables, it derives the implied single-table filters `(A1 OR A2 ...)` per table, ANDs them onto the predicate, and filter pushdown can then send them down to the scans. Before this change the rule only fired when the OR was the whole root predicate. Now it also fires when the root is an AND: it runs the same derivation on every direct OR child of that AND and appends the derived per-table ORs, skipping any that are structurally Equals() to an existing conjunct. This matters because DistributivityRule runs earlier and factors common terms (join keys and shared predicates) out of an OR-of-ANDs, which leaves `AND(common..., OR(...))`, a shape the old rule never matched. The root-OR path is unchanged except that its derived ORs are now added as separate AND children instead of being nested under one AND. That is semantically identical.
- **Trigger.** All of these must hold:
(1) The operator is a FILTER or ANY_JOIN and the expression is the root: `op.type != LOGICAL_FILTER && op.type != LOGICAL_ANY_JOIN) || !is_root) return nullptr` (join_dependent_filter.cpp:110).
(2) The matcher, unchanged from before, matches a conjunction with at least one conjunction child (lines 13-15, `Policy::SOME`).
(3) New path: the root is CONJUNCTION_AND, and for each direct child that is `BOUND_CONJUNCTION` with `CONJUNCTION_OR` (new lines in Apply, e.g. `child->GetExpressionType() != ExpressionType::CONJUNCTION_OR) continue;`), DeriveFilter's existing eligibility test applies. At least one OR branch must be an AND that references more than one table: `CONJUNCTION_AND && ExpressionReferencesMultipleTables(*child)` (lines 60-62). Some table must also have non-volatile single-table conjuncts in every branch: `if (other_it == other_entry.end()) { found = false; ...` (lines 86-89), and `table_idxs.size() != 1` excludes multi-table conjuncts (line 40).
(4) A derived OR is added only if it is not `Equals()` to an existing root conjunct or to one already added in this pass. This check is what lets the rewriter reach a fixpoint.
Only direct OR children of the root AND are examined. ORs nested deeper are not. There are no numeric thresholds, statistics, data-type checks or names.
- **Constants.** None. The change has no numeric thresholds, cardinality or selectivity cutoffs, or type restrictions. The only structural limits are that the OR must be a direct child of the root AND and that it must be join-dependent (some branch spans more than one table). Both are natural boundaries of the rewrite, not tuned values. Just outside them: an OR nested deeper, e.g. `AND(x, NOT(OR..))` or `AND(OR(AND(.., OR..)))` at depth 2, gets nothing derived. The author lists this as follow-up work.
- **Outside this benchmark.** The new path applies to any query whose WHERE clause or join condition contains an OR of per-branch multi-table AND groups next to other conjuncts. That covers both hand-written queries and queries where DistributivityRule has factored a shared term such as the join key out of each branch. Examples that are not from TPC-H:

`SELECT count(*) FROM orders o JOIN customers c ON o.cust_id = c.id WHERE o.created > DATE '2024-01-01' AND ((c.country = 'DE' AND o.amount > 100) OR (c.country = 'FR' AND o.amount > 200));`
This derives `c.country IN ('DE','FR')` (as an OR) for the customers scan and `o.amount > 100 OR o.amount > 200` for orders.

`SELECT * FROM flights f, airports a WHERE (f.dest = a.code AND a.state = 'CA' AND f.delay > 30) OR (f.dest = a.code AND a.state = 'NY' AND f.delay > 60);`
Here distributivity factors out `f.dest = a.code`, which makes the root an AND, so before this change no per-table filters were derived.

Such predicates are common in star-schema and BI-generated SQL.
- **Otherwise.** If the root is not OR or AND, the operator is not FILTER/ANY_JOIN, no OR child is eligible, or every derived conjunct is already present, the rule returns nullptr and the expression is untouched, which is the old behaviour. The root-OR case takes the same route as before; only the derived conjuncts are now flattened into the result AND (they used to be nested), which is semantically equivalent. Correctness does not depend on the derived filters being pushed down: they are implied by the original predicate, which stays in place (`conjunction.Copy()`).

## E0011: Deliminator: drop the delim join for SEMI/ANTI subqueries without blocking operators even when the LHS has a selection

Commit `91c2adb1348c`. Files: `src/optimizer/deliminator.cpp`.
Faster when accepted: q02 1.09×, q04 1.36×, q22 1.26×.
Alone on v0: 1.033× over all templates; faster q03 1.06×, q04 1.34×, q21 1.4×, q22 1.26×; slower q02 0.9×, q09 0.94×.

**Label: heuristic.** This is a heuristic: a general rule with no tie to the benchmark, but decided by plan shape alone. In its favour, it has no thresholds, names no table or column, and applies to a broad, very common class of queries: conjunctive correlated EXISTS / NOT EXISTS over flat subqueries on any schema. Turning a semi/anti delim join into a plain hash semi/anti join is a recognised decorrelation simplification. Against that, the decision ignores cardinality and cost, and it overrides an existing heuristic whose stated purpose was semi-join reduction of the subquery when the outer side is selective. The "blocking operator" proxy does not count joins inside the subquery, so some queries outside TPC-H could get slower. The author also notes that the resulting join keeps IS NOT DISTINCT FROM conditions, which block join filter pushdown. I would expect upstream to accept something like this, possibly with a cardinality-based gate.

- **Mechanism.** DuckDB plans correlated subqueries as a DELIM_JOIN. The outer side's correlated keys are deduplicated into a DelimGet, which is joined back into the subquery. Before this change, the Deliminator kept the deepest join with the DelimGet whenever the outer (LHS) side had any filter, on the theory that the deduplicated filtered keys cut the subquery's work. Now, when the delim join is a SEMI or ANTI join (a conjunctive EXISTS / NOT EXISTS or correlated IN) and the subquery side has no aggregate, window, limit, order, top-n, distinct or nested delim join, that join is removed too. The plan then becomes an ordinary hash SEMI/ANTI join on the correlation columns, with no DelimGet, no dedup HASH_GROUP_BY and no materialised duplicate-eliminated set. The idea is that with no blocking operator in the subquery, the SEMI/ANTI join already does the same filtering the DelimGet join would have done, so the extra dedup and join are pure overhead.
- **Trigger.** Inside Deliminator::Optimize, for each DELIM_JOIN candidate, all of these must hold:
(a) The old keep-deepest condition is true: `bool keep_deepest = !candidate.joins.empty() && HasSelection(delim_join);` (src/optimizer/deliminator.cpp:87). So the RHS contains a comparison join with a DelimGet child, and HasSelection finds a LOGICAL_FILTER or a non-IS_NOT_NULL table filter somewhere under the delim join (deliminator.cpp:139-161). HasSelection is called on the whole delim join, not only the LHS.
(b) `(delim_join.join_type == JoinType::SEMI || delim_join.join_type == JoinType::ANTI)` (deliminator.cpp:88). MARK, SINGLE, LEFT and INNER are excluded, so EXISTS under OR, EXISTS in the SELECT list, and scalar subqueries do not qualify.
(c) `!HasBlockingOperator(*delim_join.children[1])` (deliminator.cpp:89). The helper searches the whole RHS subtree recursively and returns true on `LOGICAL_AGGREGATE_AND_GROUP_BY, LOGICAL_WINDOW, LOGICAL_LIMIT, LOGICAL_ORDER_BY, LOGICAL_TOP_N, LOGICAL_DISTINCT, LOGICAL_DELIM_JOIN` (deliminator.cpp:48-66). It does not look at ordinary joins, cardinalities or statistics.
When all three hold, `keep_deepest = false`. Every delim-get join then goes through the existing RemoveJoinWithDelimGet. That function still has its own preconditions: the child join is INNER or SEMI, it uses column-ref conditions only, and it has the same number of conditions as delim columns (deliminator.cpp:204-226). If they pass, the delim join becomes a LOGICAL_COMPARISON_JOIN (deliminator.cpp:108-111).
- **Constants.** There are no numeric thresholds or tuned constants. The only "parameters" are the hard-coded list of operator types treated as blocking (deliminator.cpp:50-56) and the join-type test SEMI/ANTI (deliminator.cpp:88). The list is principled: these are the operators whose output depends on the whole input, or which are expensive in proportion to input size, so a pre-filtered key set could cut their work or is needed for correctness of per-group evaluation. The gap is that the list leaves out ordinary joins inside the subquery. Take `EXISTS (SELECT 1 FROM big b JOIN other o ON ... WHERE b.k = outer.k)` with a highly selective outer filter. Before, the deduplicated outer keys were joined into `big` before the inner join (semi-join reduction). Now the whole `big ⋈ other` join is computed and only then semi-joined. That can be a regression the gate does not detect. Just outside the gate, if the subquery contains, say, a GROUP BY or a LIMIT, the old keep-deepest behaviour applies unchanged. No cost model or cardinality estimate is consulted: the decision is purely on plan shape, even though the old comment says "the selection can greatly reduce the cost of the RHS".
- **Outside this benchmark.** Any correlated EXISTS / NOT EXISTS (or correlated IN / NOT IN that plans as SEMI/ANTI) that appears as a top-level WHERE conjunct, where the outer query has a filter and the subquery is a plain select-project-join with no aggregate, limit, order, window or distinct. This shape is very common outside TPC-H. Examples:
1) `SELECT u.id FROM users u WHERE u.signup_date >= DATE '2024-01-01' AND EXISTS (SELECT 1 FROM events e WHERE e.user_id = u.id AND e.kind = 'purchase');`
2) `SELECT p.sku FROM products p WHERE p.active AND NOT EXISTS (SELECT 1 FROM inventory i WHERE i.sku = p.sku AND i.warehouse_id = 3 AND i.qty > 0);`

## E0012: Join filters (min-max + bloom) for RIGHT_SEMI/RIGHT_ANTI probes and equality for deliminated EXISTS conditions

Commit `b6929da26e9e`. Files: `src/optimizer/compressed_materialization/compress_comparison_join.cpp`, `src/optimizer/deliminator.cpp`, `src/optimizer/join_filter_pushdown_optimizer.cpp`.
Faster when accepted: q02 1.08×, q18 1.08×, q19 1.05×, q22 1.16×.

**Label: general.** All three parts are principled and keyed on semantics, with no tuned constants and nothing specific to the TPCH schema or queries. Join filters on semi/anti probes are a standard sideways-information-passing technique; upstream's own comment called these cases a FIXME. Strengthening NOT DISTINCT FROM to = when the RHS is provably non-NULL is a textbook null-rejection rewrite, guarded by a conservative operator whitelist. They fire for any correlated EXISTS/NOT EXISTS/IN subquery with column equality and a flipped build side. The only reservations are about payoff, not generality. Turning off key compression for all RIGHT_SEMI/ANTI joins is a blunt workaround for the pushdown's inability to see through compress functions. The benefit was measured only on q22, and q04 was flat.

- **Mechanism.** Three changes that work together. (1) Join-filter pushdown now runs for RIGHT_SEMI and RIGHT_ANTI hash joins. The build side's min/max filter and bloom filter are pushed into the probe-side scan, so probe rows whose key matches no build key are dropped early. This is safe because these joins output only build rows, and the output depends only on which build rows found a match. (2) Compressed materialization no longer wraps the join-key columns of RIGHT_SEMI/RIGHT_ANTI joins in `__internal_compress_integral`. That wrapper stopped the pushdown from reaching the scan. Payload columns are still compressed. (3) After the deliminator fully removes a delim join of type INNER, SEMI or ANTI, it rewrites the `IS NOT DISTINCT FROM` correlation conditions to `=`. It only does this when every removed DelimGet join used plain `=` on column refs (so IS NOT NULL filters were added on the subquery columns), the condition's RHS column traces back through pass-through projections and group keys to one of those filtered columns, and the subquery subtree contains only operators that cannot add NULLs. With the right side known to be non-NULL, NOT DISTINCT FROM and = mean the same for these join types. The = condition is then eligible for join filters, which NOT DISTINCT FROM was not ("TODO: Need OR predicates").
- **Trigger.** Pushdown (A): `GenerateJoinFilters` now returns early only for MARK/SINGLE/LEFT/OUTER/ANTI. RIGHT_SEMI/RIGHT_ANTI fall through to the existing per-condition logic, which accepts only `COMPARE_EQUAL`/`<`/`<=`/`>`/`>=` and needs `PushdownJoinFilterExpression(*cond.left, ...)` to succeed, i.e. the probe key must be a plain column reachable down to a LogicalGet.
Compression (B): `compress_condition_columns = join.join_type != JoinType::RIGHT_SEMI && join.join_type != JoinType::RIGHT_ANTI && join.type != LOGICAL_DELIM_JOIN`. The condition is checked only in the existing `join.conditions.size() == 1` branch.
Equality rewrite (C): the delim join is fully removed (`candidate.joins.size() == candidate.delim_get_count && all_removed`). `CollectEqualityBindings` requires every condition of every DelimGet join to be `cond.comparison == COMPARE_EQUAL` with a BOUND_COLUMN_REF on the non-delim side. The delim join type is INNER, SEMI or ANTI. `PreservesNonNullColumns(rhs)` allows only PROJECTION, FILTER, GET, CROSS_PRODUCT, ORDER_BY, LIMIT, TOP_N, DISTINCT, WINDOW, AGGREGATE with `grouping_sets.size() <= 1`, and COMPARISON_JOIN of type INNER/SEMI/ANTI/RIGHT_SEMI/RIGHT_ANTI. A condition is rewritten if it is `COMPARE_NOT_DISTINCT_FROM` with a column-ref RHS that `TraceToBinding` maps to one of the IS-NOT-NULL'd bindings. In practice this covers a correlated EXISTS / NOT EXISTS / IN subquery whose correlation is a plain `outer.col = inner.col`.
- **Constants.** The diff adds no numeric thresholds. The only gates are join types, operator types and expression types, and each follows from a semantic argument. RIGHT_SEMI/RIGHT_ANTI output depends only on which build rows matched, so filtering probe rows by build keys is sound. Operators in the whitelist cannot turn a non-NULL column into NULL; an outer join, ROLLUP/grouping sets, or UNION would make it fail. The existing `conditions.size() == 1` gate in the compression code is unchanged upstream logic. Just outside the gates, a subquery whose body contains a LEFT JOIN, a UNION, a GROUPING SETS clause, or a non-column correlation expression (e.g. `o.k = i.k + 1`) keeps IS NOT DISTINCT FROM and gets no join filter. Plain ANTI (non-flipped) joins still get no pushdown. Whether the filter actually reaches a scan still depends on the inherited bloom/min-max machinery and build-side choice from earlier commits (E0008/E0009), which this diff does not change.
- **Outside this benchmark.** Any hash join that the build/probe flipper turned into RIGHT_SEMI or RIGHT_ANTI, i.e. a small filtered subquery side used as the build against a large probe table, with a column-ref equality key. This covers most correlated EXISTS/NOT EXISTS and IN/NOT IN-style subqueries over a big fact table, in any schema. Examples:
`SELECT c.id FROM customers c WHERE EXISTS (SELECT 1 FROM events e WHERE e.customer_id = c.id AND e.kind = 'refund');` If customers is the smaller filtered side and events is the probe, events gets a bloom/min-max filter on customer_id. The correlation also becomes `=`.
`SELECT p.sku FROM products p WHERE p.category = 'toys' AND NOT EXISTS (SELECT 1 FROM sales s WHERE s.sku = p.sku AND s.ts > now() - INTERVAL 30 DAY);` This is a RIGHT_ANTI with sales as the probe.
A cost: for every RIGHT_SEMI/RIGHT_ANTI single-condition join, key compression is now skipped, even when no filter ends up being pushed. As the author measured on q04, the bloom check over the whole scan can cost as much as the join work it saves.
- **Otherwise.** If the join type is not RIGHT_SEMI/RIGHT_ANTI, pushdown and compression behave exactly as before. If any deliminator check fails (non-equality DelimGet condition, non-column expression, a NULL-introducing operator in the subquery, a join type other than INNER/SEMI/ANTI, or a delim join that was not fully removed), the conditions stay IS NOT DISTINCT FROM and the old plan is produced. The only behaviour change outside the new paths is that RIGHT_SEMI/RIGHT_ANTI join keys are no longer compressed, even when no join filter ends up being generated.
