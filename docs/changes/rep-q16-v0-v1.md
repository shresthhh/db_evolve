## E0001: Partition distinct radix HT on group-key hash

Commit `1033aad43d8b`. Files: `src/execution/aggregate_hashtable.cpp`, `src/execution/operator/aggregate/physical_hash_aggregate.cpp`, `src/execution/radix_partitioned_hashtable.cpp`, `src/include/duckdb/execution/radix_partitioned_hashtable.hpp`.
Faster when accepted: q16 1.15×.
Numeric constants in added code: `4096`.

**Label: general.** I rate this "general". The technique is principled: partitioning the distinct pre-aggregation on the outer GROUP BY key, so each partition re-aggregates whole groups. It applies to every grouped DISTINCT aggregate, with no tests on schema, types or query shape. The only gate is one coarse cardinality floor (4096), whose origin is unexplained but which is not fitted to TPC-H's values. Two caveats keep it from being fully free: it gives up the dictionary-compressed sink fast path for distinct tables, and it has no protection against skew when there are few groups but a large estimate. Both are tuning concerns, not signs that it targets specific queries. The measured gain is only for q16, and the timings were noisy.

- **Mechanism.** For a grouped aggregate with DISTINCT aggregates, DuckDB first deduplicates (G, x) in a separate radix-partitioned hash table, then feeds the distinct rows into the main aggregate table on G. Before this change, the distinct table picked its partition from the hash of all of (G, x). Each distinct partition therefore held pieces of nearly every group, and re-aggregating a partition into the main table touched almost all groups. Now the radix-partition bits of the distinct table's hash come from the hash of G alone, and the rest of the hash (low bits used for HT slots, top 16 salt bits) still comes from the full (G, x) hash. As a result, each distinct partition holds whole groups, and its re-aggregation into the main table stays local. The prefix hash is built the same way as the main table's group hash (Hash of the first column, then CombineHash of the rest), so the partitions line up. This is standard co-partitioning on the outer grouping key.
- **Trigger.** Set up in the PhysicalHashAggregate constructor: `if (estimated_cardinality >= DISTINCT_GROUP_PARTITION_THRESHOLD)` (src/execution/operator/aggregate/physical_hash_aggregate.cpp:192). Then, for each grouping set, `if (!grouping.HasDistinct() || grouping_sets[i].empty()) continue;` (:195), and each distinct radix table gets `radix_table->partition_prefix_count = grouping_sets[i].size();` (:200). At sink time: `if (prefix_count != 0 && prefix_count < group_chunk.ColumnCount() && group_chunk.size() != 0)` (src/execution/radix_partitioned_hashtable.cpp:574). Using the first k columns as G is valid because the distinct table's grouping_set is an ordered set: the group indices are inserted first (`grouping_set.insert(group)`, distinct_aggregate_data.cpp:97), and the distinct children come after them at `set_idx + group_by_size` (:101). In short, the path is taken for any hash aggregate with a non-empty GROUP BY (per grouping set) and at least one DISTINCT aggregate, when the optimizer's cardinality estimate for the aggregate is at least 4096. There are no type, schema or query-shape tests.
- **Constants.** There are two constants. (1) `DISTINCT_GROUP_PARTITION_THRESHOLD = 4096` (physical_hash_aggregate.cpp:191) is compared against the operator's estimated_cardinality. No reason is given for it. It is a round power of two, likely chosen to avoid the cost on tiny inputs, and is not obviously fitted to TPC-H sizes: q16's aggregate estimate is far above it at any scale factor. Just below 4096 the old path runs unchanged. The cost of being on the wrong side is small either way: the change only affects partition locality, plus the loss of the compressed/dictionary fast path (see fallback). The author also points out a possible skew issue when there are few groups but a large estimate, and there is no gate for it. (2) `RADIX_MASK = RadixPartitioning::Mask(RadixPartitioning::MAX_RADIX_BITS)` (radix_partitioned_hashtable.cpp:592). MAX_RADIX_BITS = 12 is DuckDB's existing maximum ("4096 partitions ought to be enough", radix_partitioning.hpp:25-26), and Shift places it just below the 16-bit salt (:44-51). Splicing the full 12-bit window covers every radix-bit count the table may use when it repartitions. This is a structural constant, not a tuned one.
- **Outside this benchmark.** Any GROUP BY query with a DISTINCT aggregate whose estimate is at least 4096 rows, on any schema, with any key types, and including GROUPING SETS/ROLLUP (handled per set). Examples: `SELECT user_id, COUNT(DISTINCT session_id) FROM events GROUP BY user_id;` `SELECT country, device, COUNT(DISTINCT ip), SUM(DISTINCT amount) FROM web_logs GROUP BY ROLLUP(country, device);` The benefit is largest when there are many groups and each group has many distinct values.
- **Otherwise.** If the estimate is below 4096, the GROUP BY is empty, or there are no DISTINCT aggregates, partition_prefix_count stays 0 (default, radix_partitioned_hashtable.hpp) and `ht.AddChunk(group_chunk, payload_input, filter);` runs exactly as before (radix_partitioned_hashtable.cpp:600). The only change on the old path is that `sink_count += groups.size()` moved: it is now incremented in the compressed-path return and in the pre-hashed overload (aggregate_hashtable.cpp:523, :565). The count is the same, so adaptivity behaviour is unchanged. On the new path, the distinct table calls the pre-hashed AddChunk overload directly, so it skips the TryAddCompressedGroups dictionary/constant fast path. That can be a small regression for distinct aggregates over dictionary-compressed inputs.

## E0006: Exact bitmap BF for dense-int join keys on partsupp-style probes

Commit `9271a75384bc`. Files: `src/execution/join_hashtable.cpp`, `src/execution/operator/join/physical_hash_join.cpp`, `src/include/duckdb/planner/filter/bloom_filter.hpp`, `src/planner/filter/bloom_filter.cpp`.
Numeric constants in added code: `128`.

**Label: general.** An exact bitmap or range filter for dense integer join keys is a standard technique, used for example in Umbra/HyPer-style perfect filters and in "dense domain" semi-join filters. It applies to any single-key integer equality join that already qualified for a bloom filter. Nothing depends on schema, column names or query shape. The only new tuned-looking value is the 128-bits-per-row density bound. It is a plain memory-versus-precision trade-off, sits nowhere near a TPCH-specific boundary, and falling outside it simply reverts to the old hashed filter. Upstream might pick a different constant (closer to the hashed filter's ~16 bits per key, for memory parity), but the gate is broad and natural.

- **Mechanism.** When a hash join pushes a bloom filter into a probe-side scan, and the build side's single join key is an integer whose [min,max] range is small enough compared with the build row count, the bloom filter becomes an exact bitmap with one bit per value in [min,max]. It is no longer a hashed, blocked bloom filter. The bits are set from the key column of the finalized hash-table rows. The probe-side scan filter then tests a bit at offset (key - min) rather than hashing the key, so it is cheaper and has no false positives. FilterValue and zone-map CheckStatistics use the same bitmap. The join itself is unchanged.
- **Trigger.** The new code only runs where the existing bloom-filter path already applies. That path needs CanUseBloomFilter: no perfect hash table (`if (is_perfect_hashtable) return false;`), one equality key (`ht->conditions.size() == 1 && cmp == ExpressionType::COMPARE_EQUAL`), a filtered build side (`build_side_has_filter`) and an estimated probe side larger than the build side (`build_to_probe_ratio > 1.0`) (src/execution/operator/join/physical_hash_join.cpp:769-784). It also needs no cast (`!has_cast`), min != max, and non-NULL min/max (physical_hash_join.cpp:887-944). The new TrySetExactBloomFilter (physical_hash_join.cpp:821-857) then adds four conditions:
1. NULLs must not compare equal: `ht.conditions.size() != 1 || ht.NullValuesAreEqual(0)` returns early.
2. Build and probe key types must be identical: `key_type != ht.conditions[0].left->return_type` returns early.
3. The key's physical type must be INT8/16/32/64 or UINT8/16/32/64. Others hit `default: return;`. Since it checks the physical type, DATE, TIME, DECIMAL-as-int etc. also qualify.
4. The range must be dense enough: `range >= max_bits` returns early, where `max_bits = MinValue<idx_t>(EXACT_BF_MAX_BITS, ht.Count() * EXACT_BF_MAX_BITS_PER_ROW)`. In other words, max - min < min(2^32, 128 × build rows).
Nothing in the code refers to a table, column or query. The "partsupp-style" in the title is only a description.
- **Constants.** - EXACT_BF_MAX_BITS_PER_ROW = 128 (physical_hash_join.cpp:815). This is a memory budget: the bitmap may cost up to 128 bits per build row. The existing hashed filter uses `MIN_NUM_BITS_PER_KEY = 12`, rounded up to a power of two (bloom_filter.cpp:8, 99-100), so the exact filter can be roughly 5-10x bigger. In density terms, the build side must cover at least 1/128 of its key range. No measurement or derivation is given. It is a round number and does not match any TPCH size: filtered dimension tables with dense surrogate keys (part, supplier, customer, orders) fall far inside it, typically at 1-30 bits per row. Just outside it (a sparser key range) the engine silently uses the original hashed bloom filter, so the only cost is losing the speedup.
- EXACT_BF_MAX_BITS = 2^32 bits, i.e. 512 MiB (physical_hash_join.cpp:817). The comment says it matches the hashed filter's cap, and that holds: `MAX_NUM_SECTORS = 1<<26` sectors × 64 bits (bloom_filter.cpp:7). Above it, the hashed filter is used.
- The 64-byte alignment in Initialize (bloom_filter.cpp `& ~63ULL`) is a cache-line constant from the hardware.
- **Outside this benchmark.** Any equality hash join on one integer-typed key (including DATE or integer-backed types) that gets a bloom filter pushed into the probe scan: filtered build side, larger probe side, no perfect hash table, and build keys covering at least 1/128 of their [min,max] span. This is the common star-schema case of a fact table joined to a filtered dimension with dense surrogate keys. Examples:
1. `SELECT sum(s.amount) FROM sales s JOIN customers c ON s.customer_id = c.id WHERE c.country = 'DE';` (customers.id is a dense BIGINT, and the filter keeps around 5%).
2. `SELECT count(*) FROM events e JOIN users u ON e.user_id = u.user_id WHERE u.signup_date >= DATE '2024-01-01';`
3. Joins on DATE keys to a filtered calendar table, e.g. `... JOIN dim_date d ON f.date_key = d.date_key WHERE d.is_holiday`.
Not covered: VARCHAR, UUID or HUGEINT keys, multi-column keys, and very sparse key ranges such as hashed IDs or snowflake IDs.
- **Otherwise.** If any condition fails, TrySetExactBloomFilter returns without calling SetExactRange, `exact` stays false, and every changed site takes the original branch:
- InsertHashes: `bloom_filter.IsInitialized() && !bloom_filter.IsExact()` (join_hashtable.cpp:720)
- Initialize: the `if (exact)` early return is skipped
- Filter / FilterValue / CheckStatistics: `if (filter.IsExact())` is skipped
So the hashed bloom filter behaves exactly as before. One small change on the old path: CheckStatistics is now dispatched through an extra template parameter, which does not change what it does.

## E0006: Exact bitmap BF for dense-int join keys on partsupp-style probes

Commit `0ad9b3c52958`. Files: `src/execution/operator/join/physical_hash_join.cpp`.
Faster when accepted: q16 1.1×.

**Label: general.** This commit narrows the gate on an existing feature to fix a correctness bug, so it is a fix rather than new behaviour. The new condition is purely about type semantics (logical integer types only) and has nothing to do with the workload's shape. The underlying feature is a standard technique: an exact bitmap or range filter replacing a probabilistic bloom filter when the key domain is dense, gated by a generous density cap (128 bits per row) and the existing memory cap. Any filtered build side joined on a single dense integer key benefits; it does not depend on TPC-H tables, columns or sizes. The cited q16 gain (-7.3%, from 2×4 runs, with the tool's noise threshold around 5%) is weak evidence of speed-up, but nothing in the code is tied to benchmark specifics. Two limitations: the 128 constant is chosen by hand, and DATE and DECIMAL keys are now excluded even though they could be supported with raw physical reads.

- **Mechanism.** This commit only fixes and narrows the gate on an existing feature; it adds no new optimisation. The feature itself came in the parent E0006 commit. When a hash join pushes a bloom filter into the probe-side scan, and its single integer key has a build-side [min,max] range that is small compared with the build row count, the filter is replaced by an exact bitmap with one bit per value in that range. Probing it is a bounds check plus a bit test on (key - min), with no hashing and no false positives. Before this change the type gate went by physical storage type, so DECIMAL, DATE, TIMESTAMP, ENUM and similar types were accepted. For those types `Value::GetValue<int64_t>()` returns a logically cast value (for example 12.34 becomes 12), not the stored integer. The bitmap's min and range were therefore wrong, and inserting a key could hit the internal "key outside of the build-side min/max range" exception. The gate now checks the logical type and accepts only the eight plain integer types.
- **Trigger.** All of these must hold together:
(a) The join already qualifies for the normal hashed bloom-filter pushdown, `CanUseBloomFilter`: not a perfect hash table, `ht->conditions.size() == 1 && cmp == ExpressionType::COMPARE_EQUAL`, `build_side_has_filter`, and probe estimated cardinality divided by `ht->Count()` is `> 1.0`. The pushdown column must also have `!has_cast`, and the deferred bloom-filter path must be in use (physical_hash_join.cpp:775-784, 946-951).
(b) In `TrySetExactBloomFilter`: the filter is not already exact or initialised, there is one condition, and the join does not treat NULLs as equal: `bf.IsExact() || bf.IsInitialized() || ht.conditions.size() != 1 || ht.NullValuesAreEqual(0)` returns early (physical_hash_join.cpp:823).
(c) Both key sides have the same type and min/max are non-NULL and of that type: `key_type != ht.conditions[0].left->return_type || min_val.IsNull() ...` returns early (physical_hash_join.cpp:826-827).
(d) This commit's change: `switch (key_type.id())` accepts only `TINYINT, SMALLINT, INTEGER, BIGINT, UTINYINT, USMALLINT, UINTEGER, UBIGINT`; for anything else, `default: return;` (physical_hash_join.cpp:835-849).
(e) Density: `range = max_key - min_key`, and the bitmap is used only if `range < MinValue(EXACT_BF_MAX_BITS, ht.Count() * EXACT_BF_MAX_BITS_PER_ROW)` (physical_hash_join.cpp:853-857).
- **Constants.** This commit adds no constants. The constants it inherits from the gate are:
- `EXACT_BF_MAX_BITS_PER_ROW = 128` (physical_hash_join.cpp:815). This is a density cap: the bitmap may use up to 128 bits per build row, against the hashed filter's minimum of 12 bits per key (`MIN_NUM_BITS_PER_KEY = 12`, bloom_filter.cpp:8). The value is a round number, not derived from anything, but it is generous rather than tuned to a workload. A build side holding 1 in 128 or more of the values in its key range qualifies; anything sparser falls back to the hashed filter.
- `EXACT_BF_MAX_BITS = 1<<32` (512 MiB), described as "same as the maximum size of the hashed bloom filter" (physical_hash_join.cpp:816). This is an absolute memory cap.
Just outside either cap the code returns and the normal hashed bloom filter is built, so there is no cliff in correctness and only a small change in probe cost. Neither constant depends on TPC-H scale.
The type list is a principled correctness boundary: these are exactly the types whose Value accessor returns the stored integer. It is not tuned to the workload.
- **Outside this benchmark.** The path is taken by any single-key equi hash join on a plain integer key (common surrogate or serial IDs) where the build side is filtered, smaller than the probe side, and its keys are reasonably dense in their [min,max] range. Two non-TPC-H examples:
1. `SELECT count(*) FROM page_views v JOIN users u ON v.user_id = u.id WHERE u.country = 'DE';` Here `id` is an INTEGER serial and German users are scattered across the whole id range at a density of 1/128 or more.
2. `SELECT s.store_name, sum(t.amount) FROM transactions t JOIN stores s ON t.store_id = s.store_id WHERE s.region = 'West' GROUP BY 1;` Here `store_id` is a BIGINT key.
After this change, joins on DATE or DECIMAL keys (for example `orders JOIN calendar ON o.order_date = c.d`) no longer take the path; they use the hashed bloom filter.
- **Otherwise.** If any condition fails, `TrySetExactBloomFilter` returns before `SetExactRange`, so the bloom filter stays in hashed mode. `ht->SetBuildBloomFilter(true)` and the deferred push still happen, which is the pre-E0006 behaviour (physical_hash_join.cpp:950-953). For DECIMAL, DATE, TIMESTAMP, ENUM and similar keys, this commit swaps an incorrect exact bitmap that could throw for the unchanged hashed filter. Min/max and IN-filter pushdown are not affected.
