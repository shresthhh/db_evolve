## The issue

### Exact key bitmap mode for join BF on dense integer build keys

**Hypothesis.** The lineitem scan carries the l_partkey BF and is the largest operator in q09 (5.28s CPU in the profile, 60M rows in, 3.27M out). The BF is sized for 436K build rows: 12 bits/key, next power of two = 8Mbit = 1MB. Each probe does a Murmur hash plus a random load into 1MB, which mostly misses L2. The build key range from min/max is 12..1999993, about 2M bits = 250KB. An exact bitmap indexed by (key - min) needs no hashing, fits L2 and has no false positives. A sibling run measured -15% on q21 with this mechanism (128 bits/key cap).

**Plan.** In BloomFilter (src/planner/filter/bloom_filter.cpp) add an exact mode, SetKeyRange(min, range), used when the build key is integral, range <= 128 * ht count and range <= 2^31. Insert/lookup become bit set/test on (key - min). Out-of-range probes are rejected. The probe side reads the raw key values instead of hashes. In FinalizeFilters (physical_hash_join.cpp ~line 901) the min/max is known, so decide the mode there before the deferred build. JoinHashTable::InsertHashes/Finalize (join_hashtable.cpp) fills the bitmap from layout column 0 instead of hashes. CheckStatistics must handle the mode.

**Target files.** src/planner/filter/bloom_filter.cpp, src/include/duckdb/planner/filter/bloom_filter.hpp, src/execution/join_hashtable.cpp, src/execution/operator/join/physical_hash_join.cpp

**Expected gain.** q09: -5..-10%, if the BF probe is a real part of the hot lineitem scan cost (unverified; cold profile).

**Generality.** Any join BF whose build keys are dense integers, which is typical for surrogate keys and FKs.

**Risk.** Medium. Two code paths in the BF, and must keep hash mode for non-integral keys. The hot gain is uncertain because an earlier decode-side tweak on this scan gave 0% hot.



## How your change will be judged

After you finish, an automated harness that you cannot influence does the following, in order.
Failing any step sends the change back to you or retires it.

2. Static audit. Added lines must not mention the workload: no table or column names, no query

3. Build. Release build of the whole engine.
4. Correctness. Results must equal the original engine's on the visible queries, on new parameter
   values for those queries, on query templates you have never seen, on a second dataset of a
   different size, and on a suite of generic SQL over an unrelated schema.
5. Review. An independent reviewer reads your diff looking for benchmark-specific shortcuts and
   correctness holes.
6. Timing. Interleaved runs against the current best. The bar was fixed in advance:
   at least one visible template at least 5% faster (more if its timings are noisy), no visible template slower beyond its noise, and the visible geomean not slower. Templates you cannot see are not timed in this run; they only have to stay correct.

So the only changes that survive are ones that make the engine faster for a whole class of
queries. Read `.dbe/knowledge/rules.md` before you start; it is short.
