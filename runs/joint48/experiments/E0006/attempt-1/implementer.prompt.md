## The issue

### Join key-set range filter through compress projections

**Hypothesis.** q18 (695ms, 15.5%) scans all 59,986,052 lineitem rows for the l_orderkey = o_orderkey join, while only 111 orderkeys survive the HAVING semi join. The join filter pushdown cannot pass through __internal_compress_integral projections, and a single min/max range over random keys prunes nothing. A prior run (offset-aware pushdown plus an OptionalFilter OR of up to threshold ranges split at the largest gaps) measured q18 -13.6%, with lineitem scan rows going 60M→17.5M.

**Plan.** In src/optimizer/join_filter_pushdown_optimizer.cpp, follow column bindings through compress-integral projections and record the storage offset in JoinFilterPushdownColumn. In src/execution/operator/join/join_filter_pushdown.cpp (and wherever the min/max filters are built in physical_hash_join.cpp), when the build has few distinct keys (threshold < n <= 64*threshold), build an OptionalFilter holding an OR of ranges split at the largest gaps, with the offset added.

**Target files.** src/optimizer/join_filter_pushdown_optimizer.cpp, src/execution/operator/join/join_filter_pushdown.cpp, src/execution/operator/join/physical_hash_join.cpp

**Expected gain.** q18 -13%

**Generality.** Selective joins against large fact tables whose keys are clustered by row group, and pushdown through compressed materialization in general.

**Risk.** Medium. Offsets must be applied correctly, but the filters are optional (zonemap only), so a wrong pruning decision is the main risk.



## How your change will be judged

After you finish, an automated harness that you cannot influence does the following, in order.
Failing any step sends the change back to you or retires it.

1. Path policy. Only files under `src/`, `extension/parquet/`, `extension/core_functions/` may change; `test/`, `benchmark/`, `tools/`, `scripts/`, `extension/tpch/`, `extension/tpcds/`, `.github/` are off limits.
2. Static audit. Added lines must not mention the workload: no table or column names, no query
   literals, no benchmark names.
3. Build. Release build of the whole engine.
4. Correctness. Results must equal the original engine's on the visible queries, on new parameter
   values for those queries, on query templates you have never seen, on a second dataset of a
   different size, and on a suite of generic SQL over an unrelated schema.
5. Review. An independent reviewer reads your diff looking for benchmark-specific shortcuts and
   correctness holes.
6. Timing. Interleaved runs against the current best. The bar was fixed in advance:
   at least one visible template at least 5% faster (more for templates whose timings are noisy); no template, visible or hidden, slower by more than 5% (again more for noisy ones); and the visible geomean not slower. A change that makes one kind of query clearly faster and nothing slower is accepted.

So the only changes that survive are ones that make the engine faster for a whole class of
queries. Read `.dbe/knowledge/rules.md` before you start; it is short.
